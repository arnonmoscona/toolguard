# Spike B -- a small PEG for the skeleton, code for the rest

Replaces `toolguard/parser/multiline.py`'s hand-rolled `_statement_bounds_containing` /
`_split_on_unquoted_pipe` / `_classify_pipeline_sink` trio with a **second, small, separate**
PEG grammar (`heredoc_line.peg`) that parses **one physical line** into commands, words,
redirections and the operators connecting them. Python does two things only: lift heredoc
bodies by line scanning (this cannot be a PEG -- the terminator is captured on the bearer
line and matched against later lines, a backreference canopy doesn't support), and read the
sink off the parsed line.

## Files

- `heredoc_line.peg` -- the grammar, hand-written, 109 lines.
- `heredoc_line.py` -- generated by `canopy heredoc_line.peg --lang python` (offline, from
  the local npx cache; no network needed). **Generated, not hand-written or hand-maintained.**
- `sinks.py` -- `sinks(text) -> list[str]`. 114 lines, no toolguard import, stdlib only.
- `run_cases.py` -- runs all 16 cases from `CASES.md`.

## Result

```
$ uv run python run_cases.py
...
16/16 passed
```

All 16 shared cases pass, including the two the current `multiline.py` design gets wrong by
construction (see below).

## How canopy was used

Generated, not hand-rolled. `npx --no-install canopy heredoc_line.peg --lang python` (the
canopy package is already cached under `~/.npm/_npx/*/node_modules/canopy` from prior use in
this repo, so it ran with no network access). `sinks.py` walks the generated tree exactly the
way `toolguard/parser/command_model.py`'s own docstring says to: `hasattr` probing on raw
`TreeNode*` objects, never `isinstance` on the auto-numbered class names.

## What the grammar deliberately does NOT cover

- No control structures (`for`/`while`/`if`/`case`) -- see "AWKWARD" below, this is the
  spike's one real gap.
- No leading-assignment recognition (`FOO=1 cmd`) -- not in `CASES.md`.
- `$(...)` / `` `...` `` are **opaque balanced spans**, not recursively parsed into their own
  command structure. A heredoc can never belong to something written *inside* a substitution
  on the same line, so there is nothing to gain from parsing inside one -- the main grammar
  needs that recursion (for real command decomposition), this one doesn't.

Both are genuine scope-narrowing, not oversights: the whole premise of spike B is that
line-scoped attribution needs less grammar than full decomposition.

## What is judged: the four questions

### 1. How many places encode "what a quote is"?

**One**, in the grammar:

```
single_quoted <- "'" (!"'" .)* "'"
double_quoted <- '"' (escaped_char / !'"' .)* '"'
```

Referenced by name three times (`word`, `heredoc_delimiter`, `paren_body`) -- never
redefined. `sinks.py` has one 4-line function, `_delimiter_text`, that strips a leading/
trailing matching quote char off an *already-fully-parsed* delimiter token; that is
string post-processing on grammar output, not a second quote scanner, and it cannot see
anything the grammar didn't already correctly delimit.

Contrast with today's `multiline.py`: quoting is reimplemented four times, each slightly
differently and each documenting its own model (`_join_backslash_continuations`'s
single-quote-only tracker with the documented double-quote-apostrophe bug;
`_find_heredocs_in_line`'s odd-single-quote-parity count, which does *not* account for
escaped quotes; `_split_on_unquoted_pipe`'s proper single+double tracker;
`_statement_bounds_containing`'s copy of that same tracker, extended with a substitution
depth stack). Case 15 in `CASES.md` is exactly the parity-count bug in
`_find_heredocs_in_line`, and it disappears here for free because there is only one quote
definition and it is a real recursive-descent match, not a counter.

### 2. How many places encode "what a statement boundary is"?

**One**: the grammar's `control_op` rule (`and_op` / `or_op` / `semicolon_op` /
`background_op`) plus `pipe`. `sinks.py` contains **zero** statement-boundary logic --
no operator table, no character loop, no substitution-depth stack. The only thing Python
tracks is *where a heredoc body ends*, which is a different question (a body's end is a
verbatim-text-equality check against a captured delimiter, not an operator scan).

Today's `_CONTROL_OP_TABLE` + `_match_control_op` + `_statement_bounds_containing` is one
hand-rolled scanner, ~90 lines, that has to independently track quote state and a
`$(`/backtick nesting stack *while also* looking for `&&`/`||`/`;`/`&` -- five concerns
interleaved in one function. Here those are five separate grammar rules
(`single_quoted`, `double_quoted`, `dollar_paren`, `control_op`, `pipe`), each a few lines,
each nameable in a bug report.

### 3. Where does a reader look first?

**Case 5 (bare `&`)**: `heredoc_line.peg`, the `control_op` / `background_op` rule -- three
lines (`background_op <- spacing "&" !"&" spacing`). Nothing else in the codebase encodes
this, so there is no second place to also check.

**Case 6 (separator inside `$(...)`)**: `heredoc_line.peg`, the `dollar_paren` /
`paren_body` rule. Same story -- one named rule, ~4 lines, and the fact that `;` disappears
inside it is a structural consequence of PEG nesting, not a flag a maintainer has to
remember to set (contrast with `_statement_bounds_containing`'s explicit `subst_stack`,
which is exactly the kind of state a future edit can forget to update).

In both cases the answer is "one file, one rule" instead of "the one function in
`multiline.py` that does five things at once" -- that collapse is this design's central
maintainability claim.

### 4. The honest cost of a second grammar

**Against**: `&&`/`||`/`;`/`&` and quoting are now defined in two `.peg` files instead of
one. Nothing enforces agreement between them -- exactly the risk the *existing*
`_CONTROL_OP_TABLE`'s own comment already confesses to for the Python-vs-grammar case
("mirrors bash_parser.peg's control_op alternation... so a drift... shows up as a missing...
entry"). Spike B does not remove that risk, it relocates it to grammar-vs-grammar. A change
to the main grammar's operator set (unlikely, but not impossible) now has to be remembered
in two places, and the project's own `bash-grammar.md` two-phase procedure (grammar review,
then Python review) would need to run for both files on any such change. There are also now
two generated `.py` files in the repo to review diffs on, and a newcomer has one more "which
grammar owns this?" question to answer before making a change.

**For**: the overlap is small (four operators, two quote rules) and about as low-churn as
bash syntax gets -- these have not changed since the main grammar was written. The two
grammars have genuinely different *scope* (one line vs. a full multi-statement, multi-line
program with control structures) and different *purpose* (attribute one redirect vs.
decompose a whole command for rule matching), so this isn't "the same grammar copy-pasted" --
it's "the small, stable subset that both need, each written at the size its own job
requires." And the alternative -- teaching the *main* grammar to also answer "which command
owns this heredoc, before the body is even lifted" -- isn't available: the main grammar only
ever sees the post-lift, sentinel-substituted text, by construction (heredoc bodies are
context-sensitive and have to be removed before the PEG runs at all). Some place has to
parse the bearer line before lifting; the question is only whether that place is a second
grammar or hand-rolled Python, and the four questions above are the case for the former.

### 5. What this design makes EASY vs. AWKWARD

**EASY**

- Case 16 (`python <<HD | bash` -> sink `python`) falls out of the grammar for free: the
  heredoc is a redirection *on the `python` command node*, full stop -- there's no
  "last pipe segment" heuristic to get backwards. That heuristic is exactly what today's
  `_classify_pipeline_sink`/`_extract_pipeline_sink` use (both scoped to
  `_split_on_unquoted_pipe(statement)[-1]`), and it is provably wrong for this shape --
  that's what ticket 92 is.
- Case 15's apostrophe defect (P4) disappears the same way -- real quote nesting instead of
  a parity counter.
- Testing one case in isolation is one line: `heredoc_line.parse(one_physical_line)`, no
  larger context required, no need to construct a full multi-line blob to exercise the
  attribution logic.
- Adding a new redirection form (say, `&>`) is one new alternative in `redirection`, not a
  new branch in a hand-rolled scanner that also has to remember not to confuse it with `>`.

**AWKWARD**

- **The one real gap, found while probing beyond `CASES.md`**: a control-structure keyword
  on the *same line* as the heredoc bearer breaks attribution, because the grammar has no
  keyword awareness at all --

  ```
  >>> sinks("if true; then cat <<HD\nbody\nHD\nfi")
  ['then']          # wrong: should be ['cat']
  ```

  The `;` is (correctly, per this grammar) a `control_op`, so `then` parses as an ordinary
  bare command word and grabs the heredoc. This is a real gap, not a hypothetical -- a
  one-line `if ...; then cmd <<EOF` is a plausible shape. It's not in `CASES.md`, so it's
  undecided whether it's in scope for this ticket, but it should be flagged rather than
  discovered later. Fixing it means importing the main grammar's `ctrl_keyword` gate into
  this one -- exactly the "two places to keep in sync" cost from question 4, made concrete.
- The Python glue has to be fluent in canopy's generated-attribute idiom (`.text`,
  `.elements[N]`, `hasattr` probing for "which alternative matched") to walk the tree at
  all -- the same cost `command_model.py` already pays for the main grammar, so it's not a
  *new* kind of complexity, but it means this design isn't simpler than "no grammar" for a
  reader who hasn't internalized that idiom yet; the payoff is real only once that reading
  is fluent.
- Two files must be regenerated together (`.peg` source, `canopy`-generated `.py`) and both
  reviewed on every change -- the same discipline the main grammar already requires, now
  paid a second time.

## Honest weakest point

The control-structure gap above. Every one of the 16 shared cases passes, and the design's
core claim (one grammar rule per concern, versus one function doing five things) holds up
under inspection -- but the grammar's willful blindness to `if`/`for`/`while`/`case` on the
heredoc's own line is a real, findable defect, not a hedge. Whether it matters depends on how
often Claude actually emits a heredoc inside a one-line control structure -- that's a
corpus question, not a design question, and this spike doesn't answer it.
