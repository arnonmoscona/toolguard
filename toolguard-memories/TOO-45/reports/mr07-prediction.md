# TOO-45 MR-07 blind prediction -- add `package.json` as a third project-root marker

## What I read, and what I did not

I read exactly three things: the `--help` output of `tools/touch_set_inventory.py`, the full text inventory of `/tmp/canary-mr07-A`, and the full text inventory of `/tmp/canary-mr07-B` (both generated by that tool, both saved to my scratchpad). I also ran the tool's `--validate-predictions` mode three times against tree A -- twice as a deliberate *name probe* (see "Use of the validator as a probe" below), once as the final check -- and once against tree B as the final check. I listed the top-level directory entries of both trees with `ls`, which showed directory and top-level file names only.

I did **not** open, grep, glob or read any `.py` file in either tree. I did not run `git log`, `git diff` or `git blame` anywhere. I did not read anything under `toolguard-memories/`. I did not inspect either tree's tests beyond the docstring lines the inventory itself prints. I did not, in the end, read `README.md` or `docs/` from the working repo either -- the requirement was self-explanatory and the inventories answered the location question without them; my background sense of the product comes from this repo's `CLAUDE.md`, which loads automatically.

## Prediction counts

Tree A: **9** locations. Tree B: **10** locations.

## Where the change goes, and why the inventory said so

The requirement is a marker-list edit plus a search-order guarantee, so the question is only "which module owns the upward marker walk". Both inventories answer that identically and unambiguously in one entry:

```
toolguard/path_utils.py -- 363 lines
  purpose: Low-level filesystem path helpers shared across toolguard.
    - [function] iter_dirs_upward -- Yield ``start`` and each parent directory up to (and including) the home dir.
    - [function] find_nearest_marker -- Return the nearest ancestor (including ``start``) that holds any marker.
    - [class] RootStatus -- Classification of a project-root resolution.
    - [class] RootCandidate -- A candidate project root proposed from a detected marker.
    - [class] ProjectRootResolution -- Structured result of :func:`resolve_project_root`.
    - [function] resolve_project_root -- Resolve a project root as a structured, decision-free result.
```

That is about as good as a self-description gets: "walk upward", "nearest ancestor holding any marker", "a candidate root proposed from a detected marker". The *ordering* concern in the acceptance criteria maps onto `resolve_project_root` / `RootCandidate`, since a candidate-and-status model is exactly what you need to express "pyproject.toml still wins".

The second thing the inventory gave me for free is the duplication. `toolguard/config.py::find_project_root` and `toolguard/env_config.py::find_project_root` carry a byte-identical docstring first line -- *"Find the project root by searching for a project anchor or pyproject.toml."* -- in **both** trees. Two public functions with the same name and the same self-description is a duplication signal you can read straight off the inventory without seeing a line of code, and it is why I predict both rather than one. It also tells me the marker vocabulary is tiered: "a project anchor" is one thing, "pyproject.toml" is another, and `package.json` is plainly a sibling of the latter.

Test locations came out of the test docstrings, which in this codebase are unusually load-bearing. `test/unit/test_config.py::TestFindProjectRoot` announces itself as *"Real (unmocked) tests of toolguard.config.find_project_root's marker walk"* -- that is the target test, named. `test/unit/test_env_config.py::TestFindProjectRoot` is its mirror. `test/unit/test_tools_project_root.py::TestResolveProjectRoot` is the only class covering the structured resolver. And acceptance clause two is matched almost word-for-word by `test/unit/test_hierarchical.py::TestRelativeFilePathPatterns` -- *"Test that relative Read/Write/Edit patterns anchor to the project root"* -- which is the `Read(**/.env)` guarantee.

## Use of the validator as a probe

The plain inventory prints module docstrings plus public **functions and classes**. It does not print module-level constants. Since the actual marker list is almost certainly a module constant, the inventory alone could name the *module* but not the *symbol*. I used `--validate-predictions` -- the one tool I am allowed -- to resolve that, submitting guessed constant names and reading its nearest-match suggestions. Two rounds surfaced `toolguard/path_utils.py::STRONG_PROJECT_ANCHORS`, `DEFAULT_INDICATORS` and `CONFIG_ROOT_INDICATORS`, and confirmed `toolguard/tools/project_root.py` is a pure re-export (it has an `__all__` and no definitions of its own), which is why I dropped it from the prediction.

This is worth flagging honestly, because it is the one place my prediction is not purely inventory-derived. **Pre-probe, my prediction was `toolguard/constants.py` (described as "Shared immutable constants for toolguard") plus `path_utils.resolve_project_root`.** The probe showed `constants.py` holds `FILE_TOOLS`, `DIST_NAME`, `STATUS_*` and nothing root-related, and moved the constant into `path_utils.py`. So: the inventory got me to the right module for the *logic*, and got the wrong module for the *constant*; the validator corrected it. If the measurement wants the pure-inventory answer, `toolguard/constants.py` is the entry to substitute for the two `path_utils` constants.

I keep both `DEFAULT_INDICATORS` and `STRONG_PROJECT_ANCHORS`. I cannot tell from names alone which tier holds `pyproject.toml`, and a manifest file like `package.json` belongs beside it; naming both is the honest expression of that uncertainty rather than a coin flip dressed up as a prediction.

## Confidence

**Tree A: high** on the module (`path_utils.py` plus the two `find_project_root` duplicates) and on the four test classes; **medium** on which of the two marker constants actually grows. The one structural risk is that a good implementer might *consolidate* the two `find_project_root` copies onto `path_utils` rather than editing both, which would turn one of my two `decide` entries into a deletion -- still a touched location, so it should score, but the kind label would be arguable.

**Tree B: same, high**, with one extra low-confidence entry (`test/verdict_corpus/fixture_loader.py::load_fixture_sandbox`) reflecting B's own convention that behaviour changes acquire a corpus case. That is the only entry I would not be surprised to be wrong about.

## Which inventory was more informative

**Neither -- and that is the finding.** For *this* requirement the two inventories are interchangeable. `toolguard/path_utils.py` is 363 lines with the same six public symbols and the same docstrings in both trees; `constants.py` is 42 lines in both; `config.py::find_project_root` and `env_config.py::find_project_root` carry identical docstrings in both; `test_config.py` (307 lines), `test_env_config.py` (578 lines) and `test_tools_project_root.py` (230 lines) are the same size with the same class docstrings in both. My two prediction files are therefore deliberately near-identical, and that is not laziness: it is what the two inventories genuinely said.

B is *substantially* the more reorganised tree overall -- it has `api.py`, `permission_resolution.py`, `install_update.py`, `permission_migration.py`, a `RuntimeVerdict`/`UnitVerdict`/`LevelMatch` block in `config_types.py`, a `test/verdict_corpus/` package, and `tools/architecture_fitness.py`. Every one of those sits on the **decision** path. The **discovery** path -- find the root, discover config files, anchor relative patterns -- was left alone. So B's refactor bought no advantage for a change of this shape. A predictor asked "where does a project-root marker go" gets the same answer, with the same confidence, from either tree.

## Surprises and misleading self-descriptions

1. **`toolguard/constants.py` is a misleading name given its docstring.** "Shared immutable constants for toolguard" reads like the place shared constants live, and the project-root marker set is the archetypal shared constant. It is not there. This is the one self-description in either tree that actively pointed me wrong, and it did so in both trees equally.

2. **The inventory's public-symbol view hides exactly the kind of symbol this requirement edits.** A marker list is a module-level tuple, and module-level assignments are invisible in the plain report while being visible to `--validate-predictions`. For "add an item to a policy list" requirements -- a common shape -- the inventory is structurally one notch too coarse. Printing module-level constant *names* (not values) would close this gap cheaply.

3. **`toolguard/tools/project_root.py` presents as a real module and is a facade.** Its docstring ("Repo-grain project-root resolution for the migration safety gate") plus a dedicated 230-line test module reads like an implementation; "public top-level symbols: none" is the only clue that it re-exports. That is a correct reading of the tool's output, but it takes a second look, and a reader in a hurry would predict a change there.

4. **Duplicated public functions are legible from the inventory alone**, which I did not expect. Two `find_project_root`s with identical docstring first lines is a strong, cheap signal -- arguably the single most useful thing either inventory told me, and it came from a coincidence of formatting rather than from any deliberate description.

5. **The test docstrings are better navigation aids than the production ones.** *"Real (unmocked) tests of toolguard.config.find_project_root's marker walk"* names the function, the mechanism, and the fidelity level. Production docstrings in the same trees say things like "Configuration loading for toolguard". For locating a change, this codebase's tests describe themselves better than its modules do.
