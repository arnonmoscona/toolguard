# What a comment sweep found: notes on TOO-45

TOO-45 was an architecture and hygiene ticket against toolguard, a Claude Code permission hook. One phase of it, internally called punch-list item #07, was supposed to be the boring part: read every docstring and comment in the package, make the true ones shorter, delete the false ones. It ran across 72 files in the package proper, 86 test files, and 7 dev-instrument scripts over two days, unattended most of the time, using disposable single-purpose agents dispatched one file at a time. It produced about 10,000 fewer lines of prose, as intended.

It also produced sixteen tickets it was not looking for, several of them against the permission engine itself: a silent bypass in the compound-command splitter, a wildcard matcher that under-matches on exactly the patterns the project's own documentation recommends, and a fail-open in the code whose job is recording crashes. None of that was the goal. All of it came from treating a comment as a claim to be executed rather than a sentence to be read. This note is about what that produced, what it did not produce, and what of it looks like it would transfer to a codebase that isn't this one.

## The caveat first, because it governs everything after it

This is one codebase, one sweep, no control group. toolguard's comments are unusually dense with claims — "exactly when," "cannot," "the only caller," "guarantees" — and a fair amount of that prose was written by earlier AI passes over the same code, which tend toward confident universals more than a human author asserting the same fact from memory would. Nobody has run this technique against a codebase with different authorship, different age, or different claim density, and until that happens the numbers below describe this codebase's ore grade, not a general rate of return. The people who ran the sweep raised this themselves, in writing, before being asked. Treat the specific figures as evidence that the technique can find real things, not as evidence of how often it will.

## The discovery: shortening comments is not the same job as reading them

Four of the six original defect tickets from this sweep open with close to the same sentence, written independently by different agents on different days: found "by executing a docstring claim rather than reading it." That phrasing recurring on its own is itself a data point — it means the mechanism was legible to the agents doing the work, not just to whoever wrote it up afterward.

The reasoning that emerged, stated plainly rather than as a list of bullet points a reader has to reassemble: a docstring is close to the only place in a codebase where intent is stated as a universal claim and nothing downstream ever checks it. A test checks the inputs someone thought to write. A type checks a shape. A comment states a law — "matches any sequence," "cannot recurse more than five deep," "the more specific rule can be dropped with no change in behaviour" — and by construction nothing runs it, because it isn't code. That gap is old and well known in the abstract; what TOO-45 adds is a specific account of why an ordinary comment-cleanup pass would stumble into it rather than around it.

The mechanism has two working parts and they reinforce each other. The first is that the task carried an edit obligation, not a reading one: "review these comments" produces reading, but "shorten this claim, and you are accountable if the short form turns out false" produces verification, because you cannot safely compress a sentence you haven't checked. The second is that the sweep had no attention gradient. A targeted code review goes where suspicion already points; this went file by file, including the files nobody would prioritize. The clearest instance of that second effect: a five-rule over-match already live in shipped self-permission configuration was found through the docstring of an advisory analyzer that exists to warn about redundant rules, not to enforce anything — exactly the kind of file a suspicion-driven review skips.

A third factor, smaller but concrete: two scope rules forbade fixing what was found — "strings are code, do not touch them even when wrong" and "do not rewrite a false test description to match what the test actually checks." Both rules converted what would otherwise have been a silent, undocumented correction into a written finding with a reproduction. One redundancy-detector's internal message string still tells a user "this rule is redundant and can be dropped" after the surrounding docstring was fixed to say the opposite, precisely because the sweep was not allowed to touch strings. That disagreement is now on record instead of quietly gone. Prohibiting the fix increased the yield of documented defects, which is a genuinely counterintuitive way for a scope boundary to behave.

## What worked: a probe ladder, ordered by cost

The technique that did the actual finding has a shape worth naming on its own, independent of the comment-sweep framing that produced it. Four rungs, cheapest first, each with a worked example.

Direct execution is the floor: call the function with the input the docstring says can't happen. This is how the compound-command splitter's worst bypass was found — `extract_structured('while rm -rf /tmp/x; do :; done')` returns a single leaf command, `:`, and the dangerous condition is simply never presented to any permission rule. Nothing subtle was required; someone ran the function.

Brute force over a small alphabet is the next rung, and it is cheap enough to be almost free: every pattern of length four or less over `{a, b, *}`, matched against every command of length five or less over `{a, b}` — 7,623 pairs — against toolguard's own `[native]` wildcard matcher. Result: 416 mismatches across 46 distinct patterns, every single one a false negative, and every one on a pattern that does not end in `*`. A trailing wildcard fully immunizes a pattern; a leading or middle one does not. The project's own documentation advertises two worked examples of the failing shape as recommended usage. The failing input class — `*<literal>` at the end of the pattern — is not one a person writing test cases by hand tends to reach for, which is precisely why 15 existing tests for this matcher pass unchanged even when the entire hand-written matching branch is rebound to call the wrong implementation.

The third rung is a differential test against a reference implementation read straight out of the docstring's own prose. The `[native]` matcher's documentation describes an algorithm; `".*".join(re.escape(s) for s in pattern.split("*"))` under `re.fullmatch` is that same algorithm, translated literally, and it is correct on all 7,623 brute-forced pairs. When a docstring describes an algorithm rather than just asserting a property, it is an executable spec, and writing the executable version costs less than debugging the hand-rolled one.

The fourth rung is mutation testing, run out of tree: copy the repository elsewhere, delete or invert one mechanism, run the full 2,733-test suite, and see whether anything notices. The largest single run recorded 42 mutations with 23 surviving — a 55% survival rate on that batch, and roughly 50 mechanisms with zero test detection across the whole sweep, including the entire sort call inside the danger-finding report generator and the timeout on every git subprocess the installer shells out to.

Two refinements to that fourth rung are worth carrying forward on their own, separate from the sweep that produced them. First: mutate toward the fix, not only away from correctness. For a TOML string-escaping bug — an unescaped newline in a permission rule's metadata that renders a config file the parser can no longer read, silently freezing every decision to "ask" — removing all escaping produced 16 test failures, which looked like coverage. Applying the actual fix, adding the one missing escape, produced zero failures. The suite could see the bug being made worse but not the bug being fixed, which is a strictly stronger and more useful statement than "this code is untested."

Second: read the tracebacks, don't just count red. The sweep's single highest-severity finding is a fail-open in the function that logs crashes — it constructs a path using `Path.home()` above its own `try` block, and that function runs inside the hook's top-level exception handlers, before the code that would otherwise still print a decision. An unresolvable home directory during a crash converts a recoverable error into a hook that exits with nothing on stdout at all, which Claude Code cannot distinguish from no hook being installed. Injecting an unconditional raise into that function, out of tree, produced 9 new test failures, 3 of them in the hook's own test file — a naive count would call that "detected." It wasn't: all three failures were an unrelated `OSError` breaking an `assertRaises(SystemExit)` before the test ever reached a line that checks what landed on stdout. Nothing in the suite asserts the actual property at risk, which is that a decision still reaches stdout when the crash logger itself fails. Three control mutations elsewhere in the same run were correctly caught, which rules out a broken harness — this one specific mechanism is genuinely invisible, and a failure count alone would have hidden the worst finding of the whole sweep behind an apparent pass.

## Agents and the human: the same blind spot at four different scales

The most useful single pattern in this material is not "agents provide scale, judgment provides direction" — that's a platitude and this ticket's own evidence contradicts the tidy version of it. What actually recurred, independently, at every level of granularity examined, is more specific: a narrow, exhaustive check finds local truth reliably and cannot see what two or more locally-true findings mean when read together. Synthesis is a separate operation, and nothing about running more narrow checks produces it for free.

The pattern showed up inside a single function. `touch_set_score.main` has two argument guards — a mutual-exclusion check and a pairing check. Deleting either one alone leaves the test suite green, because the one test that exercises argument validation happens to trip both violations at once, so either guard catches it without the other's help. Neither deletion is a finding by itself; only the pair is, and nothing that mutates one mechanism at a time can see that.

It showed up across two tests pinning one behaviour. A takeover-mode warning function has exactly two tests. One globs a log directory that nothing in the test ever creates, guarded by a conditional that passes unconditionally when the directory is absent. The other patches a logging function that the module under test never imports — it imports only `sys`. Two different agents found these hours apart, neither aware of the other, and each filed it as "here is one weak test." Read separately, that's what they are. Read together, they say the behaviour has no coverage at all, and a third agent only caught the full picture because its brief happened to mention the sibling by name.

It showed up across three modules. Three audit-report generators each sort findings by severity, and each has a test that claims to pin the ordering. Each test's fixture happens to produce findings at only one severity level, so a same-value comparison "verifies" an order that was never actually exercised. Three different agents, three different files, three different days, three tickets that each individually read as minor — until read together, at which point they describe a security report subsystem where a reversed sort would ship and pass every test that exists for it anywhere.

And it showed up a fourth time, at a scale none of the agents were positioned to notice, because it happened inside the coordinator's own process rather than inside the code. The sweep's largest and most severe findings — the crash-logger fail-open among them — sat for days inside a 2,200-line working-notes file, each one annotated "needs a ticket, not this sweep." That annotation read as a decision and functioned as a burial: nothing was wrong with any individual note, and nobody reading the file row by row would find the pattern, because the pattern is only visible from the outside, at the level of "what does this whole file add up to." It took Arnon asking, twice, whether the sweep's biggest findings had actually been written up anywhere he'd see them, to surface tickets that had been sitting there — in one case, since before the ask, with two items already marked "fix before push." The coordinator's own retrospective note on this is unambiguous: "This is the second time in this ticket that the largest findings were left in a working queue... I wrote that about the agents and then did it myself."

That last instance is the one worth taking seriously rather than filing as an amusing footnote. It means this isn't a limitation of subagents specifically, or of LLMs specifically — it's a property of narrow, exhaustive attention as a method, and it applies to whatever is doing the narrow attending, agent or coordinator alike. The fix that emerged is correspondingly general and not clever: a product-relevant finding gets promoted out of working notes into the decision-facing artifact the same day it's found, incomplete if it has to be, rather than waiting to be tidy. Synthesis has to be scheduled as a step with its own moment in the process, not trusted to fall out of doing enough narrow checks.

Within that frame, agents did some things reliably well. They ran a 7,623-pair brute force without complaint and reported it as one more data point rather than a special event. Editors caught mistakes in the coordinator's own briefs on at least fifteen occasions, two of which had already made it into filed tickets before being caught — a five-versus-four miscount of over-granting rules, and a mis-attributed test name that turned out to be an unrelated test sharing a similar name. One editor cut a set of ticket-narrative references as noise, then grepped the actual runbook they pointed at, found the references were genuine and current rather than historical, and restored them in the same pass — self-correction happening inside a single agent's run rather than only across a review cycle. Given an explicit instruction to verify a hazard note rather than assume it, editors applied all three possible dispositions across the sweep, each with its own evidence: one false "must preserve this exact cleanup step" comment was deleted after an editor executed the step it warned against and watched it succeed; a true one was kept after grepping the code it described; a stale claim about deduplication was corrected in place after `git log -S` showed the described history had never actually happened for the file in question.

What agents did badly, beyond the synthesis gap: the single most common way an editor introduced a new falsehood was by writing a confident claim about what a mechanism *guarantees* rather than what it *does*. Across roughly thirty files, every new falsehood fit that shape — "deliberately crude in the safe direction" where the actual bias measured unsafe, "equivalence-preserving" lifted from a failure message that only proves non-equivalence when it fires, a numeric cutoff described as bounding something it does not touch at all. New prose reads as freshly checked in a way old prose does not, which makes it more dangerous per sentence, not less, and the standing rule that emerged — state what the code does and stop, don't state what that means — is aimed directly at this. Separately, and independently, the sweep needed an explicit rule against rewriting a false test description to match what the test's assertions actually check, because an accurate rewrite of a false claim produces a green test that pins nothing behind a description nobody will re-read closely again. Five different editors converged on refusing to do this without being told twice.

## The open question the sweep leaves behind, honestly unsolved

Roughly 10,000 lines of prose across 165 files were individually fact-checked against the code they describe under a standard whose explicit rule is "verify it, or cut it — never keep an unverified claim," and a meaningful fraction of what survived carries a specific recorded probe behind it: a brute force, a mutation, a grep, an execution. That is a large, one-time investment in verified truth. Nobody involved in the sweep produced an exact count of how many discrete claims that represents, and this note will not invent one.

But there is an argument that the sweep quietly made the codebase's remaining comments a *worse* passive drift detector even as it made each individual comment more likely true right now. A long, hedged comment is more likely to eventually go stale, but a stale long comment is also more likely to be *noticeably* stale — it says more, so more of it can visibly stop matching the code. A short, tightly-scoped, currently-true comment is less likely to go stale, but when it does, there's less surface area for a reader to notice the mismatch. Shortening trades a comment's passive value as a tripwire for a smaller, sharper claim that is more durable exactly because it asserts less.

The proposal that follows from that, stated as an open problem rather than a finished plan: treat the sweep's probed claims as a regression suite of prose invariants, something re-executed periodically the way a test suite is, so that a future change which silently breaks a claim's truth gets caught the same day rather than the next time someone happens to read that file closely. Unlike a diff, which shows what changed, a claim re-run localizes the failure to the exact assertion beneath it.

The honest state of this idea is that the asset exists and the mechanism does not. Nothing today records where a verified claim lives as a claim, what would re-run it, or how it would fail loudly enough to be noticed rather than silently stop mattering. A separate design ticket exists to work this out and explicitly frames itself as unfinished: "the deliverable of this ticket is a design plus a validated prototype, not a finished skill on day one." Two of its harder open questions deserve stating rather than glossing: whether the edit obligation that seems to have driven verification in this sweep is load-bearing — meaning a read-only version of this technique, one that reports claims without being on the hook for shortening them, might simply not produce the same rate of checking — and whether toolguard's ore grade, discussed at the top of this note, generalizes at all without a run against code that wasn't substantially AI-authored to begin with.

## What did not pan out, stated plainly

Not every tier of the sweep produced defects, and that's worth recording with the same weight as the parts that did. The `test/` directory — 86 files, the largest single tier by file count — produced zero product-code defects. Its yield was entirely about the test suite's own quality: catalogued cases where an assertion could not fail regardless of what the code under test did, and cases where deleting a real mechanism produced no detected failure anywhere. That is real, useful output, but it is a different kind of output from the sixteen tickets, and conflating the two would overstate what a comment sweep of test code specifically buys.

Two test files came back from full mutation testing with every deliberate mutation caught — the ones covering the permission-resolution layer and the once-per-period claim store used for daily migration and warning gating — which is worth stating because it means the suite is not uniformly blind; the blindness that exists clusters specifically in the layers where the sweep's actual defects were found, rather than being spread evenly across the codebase. And several leads the coordinator supplied along the way were checked and correctly refused by the agents doing the checking: a proposed hazard about retention exceeding a claim period turned out to satisfy the stated invariant exactly at its boundary value; a proposed restoration of deleted text would have asserted a data field that the call path in question never actually populates. Those refusals, with their evidence attached, are as much a product of this technique as the tickets are — a sweep that only ever confirmed the coordinator's own suspicions would be far less trustworthy than one that sometimes told the coordinator it was wrong.
