# TOO-45 change-role classifier - implementation report

**Revised after coordinator review.** Two changes from the first version: a factual correction to what the two validation trees are (see below), and a required feature -- definition-site symbol closure -- because the first version measured a NAME, not a VALUE, and that blind spot is worst exactly where the code is best factored. Both are addressed in full below; nothing from the first pass is hidden, but the framing and numbers in this version are the ones to trust.

## Correction: what the two trees actually are

Earlier I wrote that `allow_in_auto_mode` "was deliberately kept as an unchanged canary" across the two trees. That is wrong. `allow_in_auto_mode` did not exist in either starting commit -- it is a feature implemented FRESH in both throwaway copies, by separate agents, from the same requirement, specifically so the two implementations could be compared. Every occurrence of it in both trees is new code written for this experiment. A near-identical ratio between the trees is therefore not "expected because the flag was untouched" -- it is a genuine finding about how similarly the two architectures absorbed the same fresh requirement, and is reported as such below.

## What it does

`tools/change_role_classifier.py` is a stdlib-only dev tool that classifies every occurrence of one or more "subject" identifiers by the ROLE it plays at that location: DECISION (branch/comparison/boolean-op/predicate/match/ternary test), WRITE (assignment target, mutated, or persisted into an object/mapping), CONDUIT (transport only -- argument, return, forwarded, iterated), or CEREMONY (import, signature parameter declaration, type annotation, scope declaration). A location can carry more than one role; the single-label precedence when one is needed is DECISION > WRITE > CONDUIT > CEREMONY. The headline number is the CONDUIT-to-DECISION ratio, computed separately for production and test code (path-based split, rule stated in the tool's own output).

Three input modes: `--tree DIR` (single tree, every occurrence counts as "changed" -- the mode used for both TOO-45 validation trees, since they are independent fresh implementations, not before/after of one tree); `--old DIR --new DIR` (two trees of the same codebase, restricted via `difflib` to added/changed lines); `--repo DIR --base REV --head REV` (git diff between two revisions).

## How roles are determined (unchanged from the first pass, one bug fixed)

Resolution is AST-identity based, never substring: exact equality on `ast.Name.id`, `ast.Attribute.attr`, `ast.arg.arg`, `ast.alias.name`/`asname`, `ast.keyword.arg`, the plain-string fields on `ExceptHandler`/`MatchAs`/`MatchStar`/`MatchMapping`/`Global`/`Nonlocal`, and `FunctionDef`/`AsyncFunctionDef`/`ClassDef.name`. WRITE-target detection leans on Python's own compiler (`.ctx` is `Store`/`Del`) rather than a hand-rolled detector. Load-context occurrences walk UP the parent chain through a whitelist of transparent wrapper nodes to the nearest governing construct; an annotation field short-circuits to CEREMONY; anything unrecognised is UNCLASSIFIED with a note, never silently dropped.

**Bug found live during this round's validation and fixed**: `ast.Set` has no `.ctx` field at all (Python has no set-destructuring assignment), unlike `List`/`Tuple`. The original transparency rule guarded on `.ctx`, so it silently never matched `Set`, and every set-literal element fell through to UNCLASSIFIED. Found on the real `KNOWN_ENRICHMENT_KEYS = frozenset({ADDITIONAL_CONTEXT_KEY, ALLOW_IN_AUTO_MODE_KEY})` in `rule_entry.py`. Fixed by giving `Set` its own unconditional-transparent case; regression test `TestSetLiteralIsTransparent` added. This is exactly the failure mode the process exists to catch: a green hazard suite that never happened to exercise a real construct until real data did.

## Required change: SYMBOL CLOSURE -- the subject is a NAME, not a VALUE

The coordinator's review: verified the production count of 2 (pre-closure) against ground truth and found it defensible on raw text (~31-35 mentions per tree, almost all docstrings/comments) -- but surfaced that the *value* travels through `ALLOW_IN_AUTO_MODE_KEY = "allow_in_auto_mode"`, a `def allow_in_auto_mode(self)` property that reads it, and a `_allow_in_auto_mode_issues` validator that reads it too, at differently-spelled names throughout. Routing a value through a named constant and a small accessor/validator is normal, GOOD practice -- more likely in a well-factored codebase, not less. As built, the tool went blindest exactly where the code was cleanest, which biases every comparison toward the messier tree.

**Design.** `compute_symbol_closure(trees, subjects, hop_limit)` runs a whole-tree (cross-file) BFS, seeded from the bare subject(s), growing via three DEFINITION-SITE rules only, never name similarity:

- **string-literal-binding**: a module- or class-level `NAME = "<subject string>"` (or `NAME: T = "<subject string>"`) -- `NAME` joins.
- **own-name**: a `def`/`class` whose own name equals a seed subject -- joins at hop 1 (this subsumes and generalizes the earlier `def`/`class`-name rule).
- **reads-tracked**: a function/method whose body references (Load-context `Name`/`Attribute`) a symbol already tracked at hop *n* -- the function joins at hop *n+1*, and every name-alias assignment chain (`OTHER = TRACKED_CONST`) is grown the same way.

Once a name is tracked, its usages (including call sites, anywhere in the tree, in any file) are found for free by the EXISTING per-file occurrence scanner -- closure only decides WHICH NAMES to feed it, so no new occurrence-detection logic was needed for `.get(TRACKED_CONST)`-shaped usages.

`hop_limit` is an explicit parameter (CLI: `--closure-hops`, default 2), printed in every report. After the hop-limit is reached, the tool runs exactly ONE extra, unmerged probe round purely to populate an `excluded_by_hop_limit` list -- so a chain cut off by the limit is named, never silently absent, though this means a chain needing `hop_limit + 2` would not appear even there (stated in KNOWN LIMITATIONS).

**Precision guard, added after finding a real false-positive risk myself**: growth via "reads-tracked" excludes any tracked name that is ALSO a parameter or local variable anywhere in the candidate function (conservatively, via a whole-body scan including nested scopes) -- otherwise `def unrelated(ALLOW_IN_AUTO_MODE_KEY): return ALLOW_IN_AUTO_MODE_KEY.upper()` would wrongly pull `unrelated` into the closure on the strength of a coincidentally-shadowed parameter. Test: `test_locally_shadowed_parameter_does_not_pull_unrelated_function_into_closure`.

**Every closure member is audited in the tool's own output**: name, hop, which rule, why, and the defining location -- printed before the role counts, explicitly framed as "audit this before trusting the counts above."

### Closure hazard suite (all required cases, all passing)

`TestSymbolClosure`, 7 tests:

1. Constant bound to the subject string, read via `.get(CONST)` -- **found**, hop 1, usage found via ordinary scanning once tracked.
2. Decoy constant with a similar NAME but a DIFFERENT string -- **not found** (string-literal-binding matches on the string value, never the constant's name).
3. Helper whose name resembles the subject but never touches any tracked symbol -- **not found** (own-name requires exact match; reads-tracked requires an actual reference).
4. Two-hop chain (constant -> accessor -> call site, split across two files) -- accessor joins at hop 2, call site found.
5. Three-hop chain (constant -> accessor -> wrapper) at `hop_limit=2` -- wrapper does **not** join, but appears in `excluded`, naming the would-be hop (3) and the rule.
6. Locally-shadowed parameter (the precision guard above) -- does not join.
7. End-to-end: `run_single_tree` on a real two-file on-disk tree, asserting both the closure members and that the accessor's cross-file call site appears in `files_analyzed`.

**Fail-then-pass demonstration for closure specifically**: rather than a second naive implementation, this compared the tool's OWN pre-closure behavior against post-closure on the two-hop case (a legitimate, arguably stronger demonstration -- it is proof the tool itself had exactly the defect the coordinator flagged, not a strawman). Bare-subject matching on the calling file: **0 occurrences** (the call site totally invisible). Closure-expanded matching on the same file: **2 occurrences** (import + call site). Reproducible via `compute_symbol_closure` + `analyze_source` as shown in the test suite.

## Known limitations (also printed in the tool's own output)

The closure feature narrows, but does not close, limitation 9 from the first pass: `.get(ALLOW_IN_AUTO_MODE_KEY)` is now found (via closure), but the FINAL comparison (`value = self.metadata.get(...); return value is True`) is still invisible on both trees, because `value` is a fresh, untracked local -- closure only grows through module/class-level constants and def/class names, not through arbitrary function-local variables (that is the separate, per-occurrence alias-hop feature's job, and it is not threaded into closure growth on purpose, to keep the closure itself auditable and bounded).

New limitations added this round, concretely, per the coordinator's request:

- SYMBOL CLOSURE cannot follow: dynamic dispatch; `getattr(obj, computed_name)` where the name is computed at runtime rather than literal/tracked; a value crossing a serialisation boundary and coming back with no static link; any relationship needing more than `hop_limit + 1` hops (the excluded-by-hop-limit probe itself only reaches exactly one hop past the limit).
- The locally-bound-name exclusion (the precision guard above) is a whole-function-body, including-nested-scopes scan -- conservative in the direction of suppressing growth, meaning a genuine reference that happens to share a name with an unrelated local elsewhere in a long function would also be suppressed. Not observed on either validation tree.
- Closure's constant/alias scanning is restricted to module- and class-level simple assignments only -- it does not look inside function bodies for new constant-like bindings.

Full numbered list (12 entries) is printed in the tool's own `--` output and in the previous version of this report; unchanged entries are not re-quoted here to keep this update focused on what changed.

**One classification nuance, still true and still worth flagging**: `self.assertTrue(entry.allow_in_auto_mode)` classifies as CONDUIT (argument to a call), not DECISION, on both trees -- syntactically a call, not a `Compare`/`If`. All of both trees' `test_rule_entry.py` occurrences of this shape are this pattern, so "0 DECISION in test code" reflects a syntactic choice, not an absence of real checking.

## Third round: two real defects fixed, opaque-hop measurement added

Coordinator independently re-verified the null result (ran the tool on both trees, diffed full outputs: 154 vs 163 files, different paths/line numbers, identical role counts) and confirmed the closure listing itself -- not the ratio -- was the most valuable output, precisely because it shows both trees routing the flag through the same two-function chain at different addresses (`config.py` vs `permission_resolution.py`). Then asked for two things.

### 1. Two dropped-data defects, both real, both fixed

**`extra_notes` computed and discarded** (`_classify_ctx_node`, the walrus dual-role special case): `_walk_up`'s returned notes tuple was thrown away in favour of a fixed literal string. Currently vacuous in practice (`_walk_up` only attaches notes alongside UNCLASSIFIED, which this call site already skips), but it is real data the walk gathered and a latent trap: if a future `_walk_up` rule ever attaches a note to a SUCCESSFUL match, this would silently swallow it. Fixed by concatenating `extra_notes` into the final notes tuple instead of discarding it. Not a behavior change today; a defect the next contributor would otherwise reintroduce trust in a discard pattern that already looks intentional.

**`_error` caught and never reported** (`run_git_diff`'s whole-tree-at-head closure-discovery loop): a file fetched ONLY to grow the symbol closure (not part of the diff itself) that failed to parse was silently skipped, with no trace anywhere in the output -- exactly the silent-exclusion failure mode this tool exists to prevent, and a real behavior gap, not merely a latent one. Fixed: added `AnalysisResult.closure_parse_failures` (threaded through `_run_pipeline`), populated by `run_git_diff`, printed in its own labelled section distinct from the diff-scoped `parse_failures` list (so a reader never conflates "this file in the diff broke" with "closure discovery missed a file outside the diff"). Regression test `TestClosureParseFailuresSurfaced` builds a throwaway git repo with exactly this shape (one file in the diff, a separate broken file outside it) and asserts the failure lands in `closure_parse_failures`, not `parse_failures`, and not nowhere.

Also found, independently, while re-running validation for this round: `ast.Set` has no `.ctx` field at all (unlike `List`/`Tuple` -- Python has no set-destructuring assignment), so the original ctx-guarded transparency rule silently never matched a `Set` parent, sending every set-literal element to UNCLASSIFIED. Found on real code (`KNOWN_ENRICHMENT_KEYS = frozenset({ADDITIONAL_CONTEXT_KEY, ALLOW_IN_AUTO_MODE_KEY})`), fixed with a dedicated unconditional-transparent case for `Set`, regression test `TestSetLiteralIsTransparent` added. Third real defect found by validating on real data in as many rounds -- the pattern holding is that hazard suites built from imagination miss constructs a real, large codebase exercises within the first few thousand lines.

`pyright tools/change_role_classifier.py`: 0 errors, 0 warnings, 0 informations after both fixes.

### 2. OPAQUE HOP count -- measuring, not merely declaring, the accepted gap

Closure cannot follow a tracked symbol's value through a function-local variable (`value = self.metadata.get(THE_KEY); return value is True` -- the final comparison stays invisible). Rather than solving intra-procedural dataflow, the coordinator asked to MEASURE how often this happens, per tree, split production/test, because an asymmetry between trees would mean the DECISION counts are not fairly comparable even when they read identically.

**Rule implemented** (`_find_opaque_hops_in_scope`): within each lexical scope, an assignment (`Assign`/`AnnAssign`/`AugAssign`) to a plain local `Name` whose RHS is NOT itself a bare tracked-symbol copy (that exact case is the EXISTING, followable alias-hop feature -- counting it again here would double-count the same event) but DOES contain a tracked symbol (`Name.id` or `Attribute.attr`) somewhere in a more complex expression, AND the local is referenced again (Load) somewhere in the same flat scope, is one opaque hop. Never classifies what happens after -- purely a count plus location, exactly as asked. Printed immediately next to the role-count table, with the one-line fairness caveat the coordinator specified, split production/test/total, every location listed (never a bare number -- consistent with this tool's standing rule that a count without locations cannot be audited).

4 regression tests (`TestOpaqueHops`): the real property shape is counted; assigned-but-never-used-again is NOT counted; a bare alias copy is NOT double-counted; the report correctly splits production/test.

### Opaque-hop counts on both trees (re-run after all fixes)

- **master-copy**: production 8, test 21, total 29.
- **branch-copy**: production 8, test 22, total 30.

**Production counts are identical (8 = 8), and the underlying list is structurally identical** -- same 8 shapes in the same order (`resolved` from the `_resolve*_unclamped` helper, `auto_mode_override` from the property, `resolved` from `resolve_permission_detailed` x2, `KNOWN_ENRICHMENT_KEYS`/`value`/`issues`/`value` from the constant and validator in `rule_entry.py`), differing only in the renamed helper (`_resolve_permission_detailed_unclamped` vs `_resolve_unclamped`) exactly as the closure listing already showed. Test counts differ by exactly one (21 vs 22) -- diffing the two location lists directly shows branch-copy has one extra `resolved` hop from `resolve_permission_detailed` in its test suite, consistent with the one extra CEREMONY import occurrence already noted in the second-round report (branch's `resolve.py` imports `resolve_permission_detailed` by name where master's accesses it via a module attribute) -- not a new, separate finding, just visible again through this measurement.

**Verdict: the null result stands as a fair comparison.** The opaque-hop counts are close (29 vs 30, production exactly equal), so the earlier finding that both trees produce identical production role counts (`CONDUIT 9 / DECISION 2 / WRITE 5`, ratio 4.50 both) is not an artefact of one tree hiding more decisions behind untracked locals than the other. If anything, the opaque-hop measurement makes the null result MORE credible than it was before this round, not less -- it was the specific thing that could have quietly invalidated it, and it did not.

## Fourth round: independent adversarial review found real structural defects — previous ratios and null result WITHDRAWN

An independent adversarial agent ran 54 attack cases against the tool (full findings: `toolguard-memories/TOO-45/reports/classifier-adversarial-report.md`, read-only, not written by me) and broke it in ways that invalidate the comparison reported in the second and third rounds above. **The coordinator has already retracted those ratios and that null result to the project owner. This report does not contradict that retraction — it explains what was wrong, what was fixed, and reports new numbers that supersede everything above them.** Nothing in the second/third-round sections above should be relied on; they are kept only as a record of what was tried and why it was insufficient.

### Decision: the conduit-to-decision ratio is retired, permanently, not patched

The adversarial review's strongest finding: `sed 's/entry\.subject)/entry.subject or None)/g'` moved a tree from the worst possible ratio reading to the best with no architectural change, because `X or None` puts the subject inside an unconditionally-DECISION `BoolOp`. Wrapping `if entry.subject:` in `bool(...)` pulled the same lever backwards. Worse: a synthetic worked example showed the SAME requirement, copy-pasted inline at four call sites, scoring a perfect `0.00 (0 CONDUIT / 4 DECISION)`, while the identical requirement factored into one shared predicate function scored the WORST possible reading, `undefined (0 DECISION; 5 CONDUIT)` — the tool rated better architecture as worse, systematically, because a predicate function's own call sites (`Call.func`) and its `return`-ed decision were both terminal CONDUIT. Even after fixing that specific defect (below), the reviewer's conclusion holds: "a trivial short-circuit default and a real policy branch score identically, which is not a defect you can patch out — it is the measure being wrong for the question." The ratio is gone from this tool's output, not de-emphasized. Role labels remain as descriptive per-location annotation. The outputs this tool now stands behind are OCCURRENCE FINDING (independently verified exact against an AST oracle over 394 real occurrences across five subjects) and the SYMBOL CLOSURE listing, and the tool's own printed output and module docstring say so explicitly.

### Six defects fixed, each with dedicated regression tests reproducing the adversary's own cases

**F1 (the single most consequential defect).** `_governing_role` returned a TERMINAL `CONDUIT` for `Call.args`/`Call.func` and `Attribute.value`, so the walk stopped before ever reaching an enclosing `If`/`While`/`Compare`. `if bool(x):`, `if len(x) > 0:`, `if x.enabled:`, `if x.is_ready():`, `if isinstance(x, str):`, `if items.get(x):` and `if (found := x) is not None:` all scored CONDUIT instead of DECISION. Fixed by introducing a third walk-up outcome alongside "terminal" and "transparent": `_CONTINUE`, which records a real role (CONDUIT — the value genuinely did move through the call/attribute) and then keeps walking, so a governing DECISION found further up is ADDED, not substituted. Applied to `Call.args`/`Call.func`, `Attribute.value`, `keyword.value` (the same construct family, fixed for consistency though not itself in the adversary's example list), and `NamedExpr.value` (needed for the walrus-value, as opposed to walrus-target, case). 9 regression tests (`TestDualRoleThroughCallsAndAttributes`) reproduce every one of the adversary's measurement-table cases verbatim, plus the worked inline-vs-factored-predicate example, plus a dedicated test that BOTH roles (CONDUIT and DECISION) are present, not one replacing the other. `Subscript`, `For.iter`, `withitem.context_expr`, `Raise`, `Lambda.body`, `Return.value`, `Yield`/`YieldFrom.value` and `FormattedValue.value` were deliberately NOT given the same treatment — they were not in the reviewed, verified set, and a broader unverified change was judged riskier than a bounded, tested one. Documented as a residual gap in KNOWN LIMITATIONS with the exact reasoning.

**F3 (the defect that actually invalidated the null result).** `_closure_growth_candidates`'s growth rule admitted ANY function whose body referenced a tracked symbol anywhere, so callers of callers kept joining — on the real package, subject `command` grew a 19-name closure including `main` and `run_maintenance`, with only 58% of 142 reported occurrences actually being the subject, and closure size scaled with how finely a tree happened to be factored, putting differently-factored trees on different scales. Fixed by replacing "references a tracked symbol anywhere in the body" with "directly RETURNS a tracked symbol" (`CLOSURE_RULE_RETURNS_TRACKED`, renamed from `CLOSURE_RULE_READS_TRACKED`): a bare `return NAME` or `return obj.attr`, collected via `ast.Return` nodes reachable in the function's own scope (reusing `_flatten_scope_statements`, so if/for/while/with/try/match bodies are included, nested defs are not), minus any name locally shadowed by a parameter (reusing the existing `_locally_bound_names` guard). `return metadata.get(TRACKED)`, `return metadata[TRACKED]`, and `return TRACKED == expected` all deliberately do NOT count, even though each clearly touches the tracked symbol — that is the entire point of the fix, and it means the accessor pattern this project's own `RuleEntry.allow_in_auto_mode` uses (`return self.metadata.get(KEY) is True`) is not itself closure-tracked; the `.get(KEY)` call is still found because `KEY` is tracked directly, and the final comparison is what the new OPAQUE HOP count exists to measure (below). Verified live on the real package: subject `command` on `toolguard/` now grows to **zero** additional members (seed only) instead of 19. 8 regression tests, including a direct reproduction of the "function that consults but does not return the tracked symbol must not grow the closure" shape and a rewritten three-hop-exclusion test (the old one no longer applied once the growth rule tightened, since `return accessor()` is a Call, not a bare Name, and would never have been a candidate at all under the new rule — the rewritten version uses `return accessor` (a bare callable-forwarding return) to construct a genuine hop-3 candidate).

**F4.** Line-restriction in diff modes checked the occurrence NODE's own `.lineno`, not its enclosing statement's span, so a subject moved from a call argument into a branch test (or a DECISION's comparand edited) inside a multi-line statement could report zero occurrences with zero honesty-bucket signal — confidently wrong, the specific failure mode this tool exists to prevent. Fixed with `_enclosing_statement_span`, which walks up to the nearest `ast.stmt` and uses its full `lineno`..`end_lineno` range; `line_ok` now takes the node (not a bare int) so it can do this walk. 2 regression tests reproduce the adversary's exact two examples verbatim.

**F5.** `run_git_diff` used `git diff --name-only`, so a renamed file's pre-image was fetched at its NEW path, which does not exist at `base` — `allowed_lines` became `None` and the ENTIRE file counted as changed for a pure `git mv`, exactly the shape of a rename-heavy architecture-overhaul diff. Fixed with `git diff --name-status -M`, parsed into `_GitDiffEntry` records that carry the OLD path separately from the NEW one for renames, so the pre-image is fetched correctly. 2 regression tests: a pure rename (byte-identical content) now reports zero occurrences; a rename-plus-real-edit in the same commit still finds the new decision (rename detection must not also swallow genuine edits).

**F6.** `is_test_path` missed `spec`/`specs` directories and `conftest.py`; `--tree` pointed at a subdirectory that was itself already inside a test directory silently classified everything as production, since the "test" path component was the analysis root rather than appearing in any reported relative path. ## Fifth round: second adversarial pass, a mid-round purpose change, and the decisive test

### Purpose change, mid-round: mechanical SCORING is abandoned project-wide

Partway through this round the coordinator sent a second, separate message: the sibling instrument in this experiment (`touch_set_score.py`) was shown adversarially that ANY per-location count or rate is granularity-dependent (`surprises = L + n(1-p)`, noise scales with n, a rate just divides the signal by n) -- there is no per-location common unit between two codebases that decompose a problem differently. **Mechanical SCORING is abandoned for the whole TOO-45 effort.
