# Did the refactor help, or did it just move the code? Notes from TOO-45's architecture sweep

TOO-45 was an architecture ticket against toolguard, a stdlib-only Claude Code permission hook. Before the ticket's later phase -- a docstring sweep covered in a companion note, "What a comment sweep found" -- there was a longer, messier phase that removed two runtime dependency cycles, split a bloated config module, unified several parallel representations of a permission decision into one type, and fixed an audit-trail bug that had silently dropped 1,943 sub-command records from the security log. That work is not the subject here. The subject is what the team built alongside it to answer a harder question: not "does this code look better," but "did this measurably improve anything, or did it just rearrange the same problems into a shape that is harder to see." Five instruments were built to answer that: a static layer checker, a co-change history miner, a pre-registered prediction protocol, a suite of blind comparative implementations, and a blinded architectural judge run against already-shipped code. This note covers what each found, what each got wrong about itself, and which produced the sharpest result.

## The caveat, stated plainly

This is one codebase, one refactor, one team -- a human and an agent, on a permission-enforcement tool with unusually low tolerance for silent failure. The runtime is stdlib-only by architectural constraint, which shapes what "good architecture" even means here: no ORM to misuse, no request lifecycle, no persistence layer, no deployment topology. The judge back-test's own limitations list says so directly: this codebase "cannot exercise most architectural axes," and silence on those axes "is not evidence about them." Nothing here was run twice, on two codebases, by two teams. Every number below describes what happened once, in one place. Treat this as a report of what was tried and found, not a validated method.

## Why review alone was not trusted to answer the question

Before any of the five instruments existed, the team had direct evidence that ordinary code review does not scale to catching architectural error. A separate analysis of roughly two hundred human turns across the ticket found that the heaviest architectural objections -- a runtime cycle between two modules with no import edge between them, a phantom dependency edge, a logging module in the wrong layer -- were not raised until near the end of the work, despite having been present throughout. Those defects had already survived seven directed report agents, a blinded reviewer, the project's linter, and thousands of passing tests. What changed, by the human reviewer's own account, was not the code; it was the size of the diff in front of him: "Now that changes are fewer files I start noticing things. Even things that are not from this change set." The broader claim drawn from this is that a reviewer's detection rate is a function of change-set size and collapses toward zero below some threshold -- not from carelessness, but because a review of a large diff still *reports success*, which is the dangerous part. That finding is why the rest of this note exists: if review degrades silently on exactly the kind of sprawling change an architecture refactor produces, something other than review has to do the checking.

## What the structural numbers showed, and where they misled

The layer checker built for this ticket, `tools/architecture_fitness.py`, reads a declared layer map out of `.pyscn.toml` and checks that every module has exactly one layer and that no import crosses the map's declared direction. Under it, upward violations went from three to one, the remainder deliberately deferred. That number required a second check to trust: a two-by-two comparison of old code against old map and new code against new map, run to rule out the map itself producing the improvement. It held -- against the old map, the new code showed only the genuinely new modules as unmapped, so the reduction traced to the Python, not the configuration. But the same map is also gameable in a way nothing currently prevents: five one-line edits to it were tried against the one remaining violation, and three erased it with nothing catching the edit. Only the map's *completeness* is pinned by a real test; direction has no such anchor. The map is, in the source material's own words, "simultaneously the specification and the thing being satisfied" -- any check whose configuration lives in the same repository as the code it grades can be edited to pass without the underlying property becoming true. Nothing prevented that here except that nobody chose to do it.

A sharper instance of misleading structure showed up in the dependency numbers. Before the fix, `config` and `resolve` -- two modules with zero import edges between them -- called each other 46,481 times over a 6,401-case replay, entirely through an injected callback no static tool could see. After the fix, the same call volume happens with both ends now inside one layer connected by an ordinary import edge the cycle detector can at least see. Meanwhile the number of times `config`-layer code actually executed on the decision path fell 87 percent, from roughly 2.9 million calls to roughly 380,000 -- while `config`'s static fan-in, the number most import-graph tools would report, went *up* by one. A tool measuring only import edges would have called this change neutral to slightly worse; the runtime trace said the opposite. That gap between static structure and runtime behavior is precisely what the whole phase was built to close.

The co-change history miner in the same tool gave the cleanest example of a metric moving for a reason unrelated to what it claims to measure. It counts file pairs that change together "100 percent of the time," grouped by ticket rather than raw commit specifically to stop someone gaming the count by splitting commits. Under that grouping, fully-coupled pairs rose 89 percent over the refactor -- 71 to 134 -- reading, on its face, as coupling getting dramatically worse. Under plain per-commit grouping over the identical changes, the same metric rose only 8 percent. The gap traced entirely to file pairs crossing a fixed observation-count threshold the tool uses to suppress coincidence, purely because TOO-45 was committed as a few large commits rather than many small ones. The anti-gaming design -- group by ticket, not commit -- is exactly what produced the false signal.

## Predictions written down before the work: the surprise-factor protocol

Before each of seven punch-list items, a blinded agent -- given only the ticket text, a bare file inventory (path, line count, first docstring line), and the layer map, explicitly with no repository access -- predicted which files the work would touch and where change would concentrate. After the work, the prediction was scored: hits, misses ("surprises"), overshoots, with every surprise assigned a cause -- ordinary estimator ignorance, a hidden dependency, prose coupling (a name or string coupling two places the import graph doesn't show), scope creep on the implementer's part, or a genuine latent defect.

Two corrections to the protocol's own design stand out. An early headline metric -- actual touch-set size over predicted size -- was dropped outright after it inverted against the recall score on every comparison where both were computed; the team cut it rather than keep reporting it "for continuity." More consequentially, the protocol's designer corrected its stated purpose midway through: "The surprise metric is not supposed to predict the actual. It is supposed to align with my expectations... recall against the actual touch set is a property of the world, not of the instrument." That is a redefinition of the goal, made explicitly and in writing -- evidence the team treated its own measurement design as falsifiable rather than fixed.

Across the six items scored, recall ranged from 36 percent (worst) to 80 percent (best), and moved in ways that revealed the estimator's own behavior. On one item, learning that precision was being scored, the estimator visibly narrowed its net on the next item -- twelve predictions instead of twenty-five -- reasoning in its own write-up that "predicting them would be hedging, and hedging is what precision scoring punishes": a Goodhart effect observed directly inside a seven-item series. On four items the estimator also predicted its own future misses correctly, by naming its uncertainties in advance; one write-up records this as "five for five, every miss described in advance, by mechanism, by the thing that missed it." An instrument that can say in advance where it expects to be wrong is doing something more useful than one that is simply right or wrong.

The protocol also caught something about the tickets themselves: two of the seven items' own written justifications turned out measurably wrong once someone tried to predict against them. One claimed sixteen hand-rolled error-output call sites; the actual count was eight. Another claimed four independent sets tracking which tools the system governs; the actual was three live plus one dead, plus three more undocumented copies the ticket never mentioned. Both were flagged as evidence the tickets were "written from a code reading rather than a count" -- the same failure mode the comment-sweep phase found inside prose, here found inside the planning documents that preceded the work.

What the protocol did not do is produce a verdict on itself. Its own closing statement defers judgment: the deliverable is "not a verdict on which measures work" but "a measure plus a mechanism that keeps measuring it," on a timescale of months. That should be read as a limitation, not a soft landing -- the individual findings above are real, but nothing here has been shown to generalize even within this one codebase.

## Blind comparative implementation: what the canaries found

A second family of instruments implemented something small and new, once against the pre-refactor codebase and once against the refactored one, by an author blind to both trees' history, then compared. The first version -- a "micro-canary" -- planned to score the comparison mechanically, by a ratio of source locations touched or by role concentration. Before a single canary was implemented, a Monte Carlo simulation of both proposed formulas showed each was structurally biased toward whichever tree happened to be more coarsely decomposed, regardless of which was actually better factored -- one metric picked the coarser tree in roughly two-thirds of simulated draws even when the finer-grained tree was objectively better structured. The reason, in retrospect: there is no shared unit of comparison between two codebases that decompose the same problem differently. Both mechanical metrics were abandoned before use, a third was never built, and the team's own framing treats this as a result, not a failure: three of four planned numbers were proven unusable before they cost more than four agents' worth of design work.

What replaced mechanical scoring was blunter: a blinded judge asking, for each location a small requirement's implementation touched, whether a careful reader of the requirement would expect that location to change. Of twelve pre-registered requirements, four were actually implemented and scored (the staging plan for the rest does not reconcile with what was reported). One showed the refactored tree clearly ahead; two came back null -- identical footprint, identical pre-existing bug independently rediscovered in both trees; one reversed outright. In that fourth case the pre-refactor tree was rated easier by its own implementer, and the refactored tree harder -- because the "easier" implementation had silently introduced a real upward-layering violation nothing could see, while the "harder" one had correctly discovered and respected the boundary. The write-up does not soften it: "so 'straightforward' was straightforwardly wrong." That false signal led to a real fix, a new layer introduced specifically for the cross-cutting code that caused the confusion. Every one of the four canaries, not only the reversed one, also surfaced a real pre-existing product defect nobody had gone looking for -- two disagreeing definitions of a project root, two independently hardcoded copies of a tool list in the same file. In this small sample, implementing a plausible requirement found more live bugs than reading the code for them did.

A related, larger canary took the opposite design: the same author built one deliberately cross-cutting feature completely, once in each tree, in a single sitting. Its headline finding cuts against the tidy version of the whole exercise: the feature was "natural in both trees, not free in either," and the refactored tree's implementation was not even smaller (thirteen files, just over a thousand inserted lines, against twelve files and under a thousand). The refactor's advantage showed up specifically rather than generally: one real security edge case was cleanly closeable in the new tree and not at all in the old one; a hand-built test double broke against the old tree's interface and not the new one's; the layer checker caught a real wiring mistake immediately in the new tree, with nothing in the old tree able to catch the equivalent error. That is a more honest result than "the refactor made everything easier" -- it bought three specific, checkable things, not a smaller feature.

A third, unrelated set of twelve fixed "guard canary" probes, built earlier to safety-net an unattended agent loop against breaking permission enforcement while working, turned out to have zero measured sensitivity to the TOO-45 changes for most of the ticket -- they were checking the separately-installed release binary rather than the branch under development. Pointed directly at the branch, they still found nothing, confirmed by execution rather than assumed. They were kept anyway, reframed: not as evidence the refactor was safe, which they were never capable of showing, but as a check against a stale local install silently shadowing the code someone thinks they are running.

## When the ruler is made of the same material as what it measures

The clearest instance of a probe sharing a defect with the thing it probes is the layer map itself: simultaneously the specification the checker validates every import against, and a plain configuration file editable, independently of any Python change, to make a violation disappear. That held only because nobody exploited it -- the checking tooling has no way to distinguish "the code got better" from "the ruler got shorter." A near neighbor appears in the reassessment of one deferred punch-list stage, whose own violation detector was blind to five of six ways code could evade the exact rule it exists to enforce, with its one genuine catch fixable by relabeling rather than restructuring. Neither is the sharpest possible version of this failure -- a probe literally built from the same buggy helper function as the code it checks -- and no instance of that exact shape turned up in the material read. But the weaker version found twice here still generalizes: a check is only as independent as the distance between where its rules live and where the code it grades lives, and when both sit in the same repository under the same deadline, that distance can be small enough to matter.

## The sharpest single result: a judge re-reviewing its own team's shipped work

The most pointed instrument in this phase ran last, after five punch-list changes had already been written, reviewed, and committed. Eight independent, blinded judge instances -- one brief each, one subject each, no access to any prior analysis, no visibility into each other's output -- evaluated architecture only, across twelve fixed axes (coupling surface, dependency direction, locality of change, and others), explicitly told to ignore anything that looked like an ordinary bug. Five reviewed already-merged diffs; three reviewed pre-implementation proposals that had already been caught and revised by ordinary review before they became code, to see whether the judge could still find something in the version that never shipped.

The judges found eight live defects in code that had already passed review and shipped, two marked serious enough to fix before the next push. The kinds matter more than the count. One collapsed four genuinely different lock-failure reasons into a single status value, so the caller renders a wrong explanation and silently drops a day's intended work -- the same shape of defect the comment-sweep phase spent two days finding inside docstrings, here found inside shipped logic. One used dynamic attribute lookup to call a function by name specifically so an existing test's patch target would keep working, making the call invisible to ordinary call-hierarchy tooling. One was an incomplete migration: the calling code still hand-rolled the exact duplicated logic a new shared component had been built to remove. And one -- most pointed for this note -- was a runtime cycle invisible to the static layer checker, in code written after the phase's two flagship cycle removals had already shipped, of the same shape those removals existed to eliminate. Fixing the instances did not fix the pattern generating them.

As of the most recent check against the working tree, neither "fix before push" defect has actually been fixed; both remain open, one queued since the day the judge found it -- a fact about what happens to a finding after it is made, not a criticism of the judge.

The judge's own limitations are stated candidly, and the sharpest is a negative result: on the one case where the same defect appeared once in a pre-implementation proposal and once in the diff that resulted from it, the judge caught it in the proposal and missed it in the diff. The stated conclusion: "the judge sees architectural defects in proposals and not in diffs." If that holds beyond this one case, it argues for moving architectural judgment earlier, to the design stage, rather than treating a post-hoc review as a reliable backstop once the code exists. No cost figure for running the eight judges was recorded anywhere; a separately-cited figure, roughly three dollars and ten minutes for a single blinded review pass, belongs to a different, more general review practice and should not be attached to this instrument.

## What did not pay for itself

A ticket filed specifically to decide whether three dev-only measurement scripts should be kept or deleted remains open and undecided, and does not lean toward an answer: one submetric was independently verified exact against an outside check, while a headline metric on a different script was shown anti-correlated with actual code quality, scoring hand-copied code better than properly factored code. It ends with a menu of three options, not a recommendation. A separate change-cost metric, meant to track how much code a small enrichment would touch, read the same number at every measurement point across the entire ticket regardless of what changed, rose when coupling was removed (because removed coupling turned anonymous tuple positions into named fields the counter treated as new), and was shown defeatable by a simple rename -- verdict, in the source's own words, "a compromised instrument; must be replaced." Two general-purpose static-analysis tools tried as substitutes for the purpose-built layer checker were both rejected on direct evidence: one reported clean on a specific line the layer checker correctly flagged; the other produced over eleven thousand findings on the codebase's docstrings, nearly all pure formatting noise, unrelated to the actual problem of comments that were too long rather than malformed.

None of this adds up to "the machinery was a waste" -- every negative finding came from checking an instrument rather than trusting it. But set against the surprise-factor protocol's own closing admission -- that every architectural error caught in this ticket was caught by a human asking a direct question, and none by any metric, blind agent, or automated test -- the honest summary is narrower than "we built instruments and they worked." It is closer to: architectural correctness, on this ticket, was caught by attention, not measurement, and the measurements were most valuable not when they confirmed the architecture had improved, but when checking them for bias taught the team what a proxy metric cannot see.

## What seems worth carrying elsewhere

Three things look like they would transfer past this codebase, stated as narrowly as the evidence supports. First, any before-and-after structural number is worth a deliberate adversarial pass asking whether the instrument's own configuration could produce the improvement without the code changing, before the number gets reported as a result -- here that pass caught nothing wrong in one case and found a real, unexploited gap in another. Second, writing a prediction down before the work, and being willing to redefine what the prediction is even for partway through, produced real information about both the codebase and the people estimating it, including catching two written justifications for the work that were measurably wrong before a line of code changed. Third, and least comfortable: a dedicated, narrowly-scoped review run after the fact found real defects in code multiple other checks had already passed, but did this more reliably on work not yet built than on work already shipped -- a specific, checkable argument for moving architectural scrutiny earlier, not a general endorsement of one more review pass at the end.
