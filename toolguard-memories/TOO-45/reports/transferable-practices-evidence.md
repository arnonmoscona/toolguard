## C. WHY the sweep found what it found (TOO-52 mechanism hypothesis — 4 parts)

Source: scratchpad claim-falsification-skill-ticket.md, "The mechanism hypothesis" section. This is the fullest reasoned account and matches the brief's framing closely.

1. **A docstring is the only place intent is stated in universally-quantified form and nothing ever checks it.** Tests check inputs someone thought of; types check shapes; comments state laws nothing reads. Six concrete false-claim examples given (prefixes_overlap, uninstall_readiness.py, redundancy._normalised_body, hierarchy.py x3, multiline.py depth limit, install_update.py git-hang claim).
2. **The edit obligation converted reading into executing.** "Review these comments" produces reading; "shorten this claim, and you are accountable if the short form is false" produces verification, because you cannot safely compress a claim you haven't checked. Framed as "the least obvious part and possibly the most important," and as "the sharpest open question in the ticket" whether a read-only skill (no edit obligation) would reproduce the effect.
3. **No attention gradient.** File-by-file sweep, including boring files. Worked example: the `permissions.py:163` over-match (5 shipped self-permission rules over-granting) was found via the docstring of "an advisory analyzer nobody would prioritise reviewing."
4. **A scope boundary that forbids fixing forces documenting.** Two rules barred correcting what was found: "strings are code, do not touch them" and "do not rewrite a false Given/Then." Both converted would-be silent fixes into written findings. Ticket 22's HR2 row (redundancy `note` string) exists only because the agent was forbidden from quietly correcting a string. Framed explicitly: "prohibiting the fix increases the yield."

## D. The probe ladder — methods that worked, with measurements

Source: scratchpad ticket, "The probe ladder" section + individual tickets.

1. **Direct execution.** Found P1-P5 in compound splitter (ticket 19), including `while <dangerous>; do :; done` -> shell unadjudicated bypass.
2. **Brute force over tiny alphabet.** Ticket 17: 7,623 pattern/command pairs (patterns len<=4 over {a,b,*}, commands len<=5 over {a,b}) run in well under a second. Result: 416 mismatches across 46 distinct patterns, ALL false negatives (never false positive), all on end-anchored patterns (trailing `*` fully immunises). Most common failing shape `*<literal>`, 280/416. Ticket 18 (DEFAULT multi-token over-match): 79,401 pairs (per TOO-52 doc — NOTE: could not independently verify 79,401 from ticket 18 file directly since I did not open it; sourced from scratchpad claim-falsification doc's probe-ladder section, treat as secondary).
3. **Differential against reference implementation derived from the docstring's own prose.** Ticket 17's reference: `".*".join(re.escape(s) for s in pattern.split("*"))` under `re.fullmatch`. Correct on all 7,623 pairs; simpler than the cursor walk; became fix option 2 in the ticket. Framed: "When a docstring describes an algorithm, it IS an executable spec."
4. **Mutation testing, out-of-tree.** Copy repo out of tree, delete mechanism, run full 2,733-test suite, count failures above a measured ~2-error environmental floor.

### Wording-precision worked example (ticket 17)
First characterisation of the failing class ("whose final literal also occurs earlier in the command") was tested as a predicate: under-fired 0 times but **over-fired on 204 pairs** (counterexample: NATIVE 'a*a' vs 'aa' matches correctly because the earlier 'a' was consumed by a preceding segment). Corrected wording: "found before the end of the command, relative to the scan position." Caught by an editor re-verifying a reviewer's proposed sentence rather than pasting it verbatim.

- Core logical claim (mine to construct, is sound given B/C above): shortening a comment makes the remaining claim MORE likely true (verified) and therefore less likely to silently drift into falsehood over time = a more durable, narrower claim. But a shorter, narrower, true claim is also less likely to accidentally catch a future code change that violates its spirit — i.e., it's a less sensitive tripwire. Net: the sweep traded a large volume of unreliable passive documentation for a smaller volume of reliable-at-this-moment documentation, which is a REDUCTION in passive drift-detection surface even as it's an increase in the value of any given surviving claim if actively re-executed.
- **We have the asset, not the mechanism** — directly quoted from scratchpad ticket: "Nothing today says where a verified claim lives, what re-runs it, or how it fails loudly." TOO-52 is explicitly a DESIGN ticket, not a built skill: "The deliverable of this ticket is a design plus a validated prototype, not a finished skill on day one." Not done yet, explicitly: "Why this is not being done now... TOO-45 has too much in flight already."
- TOO-52's proposed shape (for context, not necessarily to use in full): claim extraction via quantifier-token scan (every/always/never/only/all/none/cannot/impossible/exactly when/identical/guarantees/ensures/prevents/no change/must) -> classify (falsifiable/unfalsifiable/out of scope) -> probe (cheapest ladder rung) -> verdict table. Explicit non-goal: read-only, does not edit the comment (avoids the new-prose-reads-as-verified failure mode, preserves the forbid-the-fix lever).
