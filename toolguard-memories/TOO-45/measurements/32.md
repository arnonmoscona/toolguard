# Ticket 32 item 1, measured 2026-08-21 — HALF fixed, and the surviving half is worse than the ticket says

## What was fixed

`migrate()` (`permission_migration.py:~1250`) now branches on the reason and emits two different warnings — a timeout message and a generic *"exclusive access could not be guaranteed ({reason})"*. **`migrate()`'s own prose is correct.**

## What is still live

**It still returns `MigrationOutcome.DECLINED_LOCKED` for all four reasons.** `file_lock` distinguishes `REASON_TIMEOUT`, `REASON_NO_PRIMITIVE`, `REASON_DIRECTORY_UNAVAILABLE`, `REASON_FILE_UNAVAILABLE`; the enum collapses them.

So the **second** caller still cannot tell them apart. `auto_migrate.py:122`:

> *"[TOOLGUARD AUTO-MIGRATION] Another migration is already running for this project; skipping."*

announced for **all four**, including *"no OS advisory-lock primitive available on this platform"* and *"lock directory unavailable"*. **That statement is false in three of the four cases.**

## THE SEVERITY THE TICKET UNDERSTATES: a permanent silent disable

`run_auto_migration`'s own docstring:

> *"The day's slot is claimed immediately before `migrate()` ... **Nothing releases the claim afterwards**, so a migration that fails or is declined waits for the next day rather than retrying."*

Burning the day is **defensible for `REASON_TIMEOUT`** — another migration is running and will do the work.

It is **not defensible for `REASON_NO_PRIMITIVE`**, which is a property of the *platform*, not of the moment. On such a machine, every day: claim the slot, fail to acquire, burn the claim, print a false explanation. **Auto-migration never runs, ever, and the user is told the cause is a concurrent migration that does not exist.**

Same for `REASON_DIRECTORY_UNAVAILABLE`/`REASON_FILE_UNAVAILABLE` while the underlying condition persists.

**This is a fail-open-and-say-nothing defect wearing a fail-closed message** — the campaign's signature shape, and its worst variant, because the message actively misdirects the person who could fix it.

## Why this is the textbook case for the project's own rule

The global CLAUDE.md cites this ticket by name: *"four lock reasons collapse to one and a false message is announced from what survives."*

**The half-fix is the instructive part.** Someone corrected the prose **at one renderer** while leaving the structure collapsed, so the *other* renderer — a different module, with no data to render correctly — still lies. That is exactly the rule's corollary:

> *"If you find yourself writing a regex against a message your own program produced, the structure you needed was discarded upstream. **Restore it there** — do not improve the regex."*

Fixing `migrate()`'s wording without widening `MigrationOutcome` is the same error in a milder form: improving one rendering instead of restoring the fact.

## Fix direction

Carry the reason on the outcome — either a `DECLINED_UNAVAILABLE` member distinct from `DECLINED_LOCKED`, or a reason field on the returned value. Then:

- `auto_migrate` says something true, and
- **it can decide whether to burn the day.** A timeout should; a missing lock primitive should not.

The second consequence is the one that matters and it is **unreachable without the structural change** — no rewording can give the caller a fact it never received.

# Item 2, measured 2026-08-21 — the DEFECT is real, the JUSTIFICATION is false, and that changes its priority

The ticket says `_dispatch`'s `getattr(error_log, rule.log_fn_name)` leaves `log_warning`/`log_error` with **"zero static callers"** — *"invisible to pyright's `incomingCalls` and to `callers_of`"* — and marks it **fix before push** on the strength of *"what static analysis cannot see, a reader cannot either."*

**Measured: they have four static callers.**

```
hook.py:35   from toolguard.error_log import log_conflict, log_crash, log_error, log_warning
hook.py:89   log_error(issue.message, issue.corrective_steps, log_dir)
hook.py:91   log_warning(issue.message, issue.corrective_steps, log_dir)
hook.py:397  log_warning(...)
hook.py:947  log_warning(divergence.warning_message, ...)
```

So the functions are **fully visible** to pyright and to `callers_of`. Anyone asking *"who calls `log_warning`"* gets four real answers immediately.

**What is actually true** is narrower: the *reporter's* edge is invisible. You cannot statically see that `error_reporter` routes to them, so the call graph is missing one edge out of five — not a function that nobody appears to call.

**And the indirection is documented, with its reason, at the field itself** (`error_reporter.py:52-55`):

> *"resolved via `getattr` at dispatch time rather than bound here, so a test's `patch.object(error_log, "log_warning", ...)` still takes effect."*

## Disposition — DEFER CANDIDATE, flagged for Arnon

The ticket's characterisation — *test-patching mechanics driving a production indirection* — is **accurate and worth fixing on design grounds**: bind the callable, patch the reporter in tests. That is a real improvement.

But the argument that promoted it to **fix before push** does not survive measurement. The premise was that the functions are invisible; they are not. **This is a design smell with one missing call-graph edge, not a mechanism hiding from its readers.**

Per `.claude/rules/evidence-before-fixing.md`, this is the shape that should move down the queue rather than gate a push: no runtime consequence, no silent failure, nothing a user can encounter. **Contrast item 1**, which permanently disables auto-migration on a platform without advisory locks while announcing a false cause — that one earns its marking and more.

**Recommend: item 1 fix now, item 2 demoted to ordinary priority.** Arnon's call, since he marked both.

## The pattern worth naming

**A true observation attached to a false justification.** The indirection is real; *"zero static callers"* is not. Checking the justification rather than the observation is what separates a fix-before-push from a nice-to-have — and only the justification was checkable in seconds.

**Third instance this campaign** of a ticket's *severity claim* failing while its *defect* held (with tickets 18 and 70). The defect being real is not evidence the priority is right.
