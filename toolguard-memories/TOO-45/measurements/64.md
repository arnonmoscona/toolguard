# Ticket 64, measured 2026-08-21

## CORRECTION FIRST — my earlier measurement was about the wrong module

An earlier version of this file analysed `file_lock` adoption across `config_write_guard` / `permission_migration` / `installer` / `rule_apply`, and called it *"ticket 64's premise"*.

**Ticket 64 is about `toolguard/tools/decision_ledger.py`.** Its defect 2 is `record_decision`. I read the ticket's title — *"the ledger writer has no lock"* — mapped "ledger writer" onto the config-writing machinery I had just been looking at for ticket 20, and measured that instead. **Third error today of the same family: a conclusion from adjacency rather than from the thing itself.**

The analysis is not wasted (see the transferable part below), but the attribution was wrong and the file is rewritten rather than patched.

## Defect 2, verified live at HEAD

`toolguard/tools/decision_ledger.py`, `record_decision`:

```python
existing = [d for d in load_ledger(path) if d.id != decision.id]
existing.append(decision)
path.parent.mkdir(parents=True, exist_ok=True)
path.write_text(json.dumps(...) + "\n", encoding="utf-8")
```

**Read-modify-write with no lock and no atomic replace.** `write_text` truncates and rewrites in place, and `file_lock` appears nowhere in the module (grepped: zero hits).

**The module's raise-on-corrupt policy is what sharpens this.** A torn write does not degrade — `load_ledger` throws, so a half-written ledger is a hard failure on every subsequent read, not a lost entry.

Defect 1 is **fixed** (`level` derived from the path, not the body).

## The transferable part of the earlier work — it applies here, correctly this time

`file_lock.py` is complete and has **exactly one adopter**: `permission_migration.migrate()` (`:1244`), from ticket 15. `decision_ledger` is a second unlocked read-modify-write.

**And the design point holds for this module specifically**: the lock must span `load_ledger` -> `write_text`, because that is the transaction. A lock acquired inside a write helper opens *after* the read, which is exactly too late — two concurrent `record_decision` calls would each read the same list and the second would erase the first's entry. **So "add an atomic write" is necessary but not sufficient; atomicity prevents a torn file, not a lost update.**

Both properties are wanted, and they are different:
- **atomic replace** (write to a temp file, `os.replace`) -> no torn file, no raise-on-corrupt failure
- **exclusive lock spanning load->write** -> no lost update

## Reachability — this is a hook-path writer, unlike ticket 20's

toolguard runs **one process per tool call**, so concurrent `record_decision` calls are reachable whenever two tool calls overlap. That is a materially better exposure story than ticket 20's config writers, which are human-initiated and rare.

**Measure before briefing**: whether `record_decision` is actually called from the hook path or only from `--ledger-*` CLI subcommands. If CLI-only, the concurrency argument weakens sharply and this becomes a correctness-hygiene item rather than a live race. **I have not checked this.**

## REACHABILITY MEASURED — CLI-only, and it inverts the ticket's priority

I flagged above that I had not checked whether `record_decision` is on the hook path. **It is not.**

- Sole caller: `maintenance.py:1094`, inside `_run_record_decision`, reached only from the `--record-decision` CLI flag.
- **`hook.py` does not import `decision_ledger` at all** (zero occurrences).

So my "one process per tool call, therefore concurrent" argument **does not apply**. A lost update needs two simultaneous `toolguard-maintain --record-decision` invocations — a human running the CLI twice at once.

### The two defects have very different exposure, and the ticket leads with the weaker one

| defect | what it needs to fire | reachable? |
|---|---|---|
| **lost update** (no lock) | two concurrent CLI invocations | **unlikely** — human-initiated, non-overlapping in practice |
| **torn write** (no atomic replace) | **one** process interrupted mid-`write_text` — Ctrl-C, crash, disk full, OOM | **yes, single-process** |

**The atomic write is the valuable half.** `write_text` truncates before writing, so any interruption leaves a partial file — and `load_ledger` **raises** on malformed input, so the ledger is unreadable from then on, not merely missing an entry. That is a single-process, no-concurrency-required path to a hard failure.

**The lock is the low-value half**, and the ticket's title leads with it (*"the ledger writer has no lock"*).

### Recommended scope — atomic write now, lock deferred

Do the **atomic replace** (temp file + `os.replace` in the same directory). It is small, removes a single-process failure mode, and needs no design decision.

**Defer the lock** and flag it for Arnon: it guards a race that requires deliberate concurrent CLI use, and per `.claude/rules/evidence-before-fixing.md` that is the deliberate-reachability profile that belongs at the bottom of the queue. **Do not fold it in silently** — the ticket asks for it by name, so skipping it is a decision to record, not an omission.

**Note the shape**: the ticket names the mechanism it wants (`file_lock`, by analogy with ticket 15) rather than the failure it fears, and the named mechanism turns out to address the rarer of its two defects. **Measuring reachability separately for each defect in a ticket — not for the ticket as a whole — is what surfaced it.**
