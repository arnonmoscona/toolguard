# Ticket 85 — the external contract surface, mapped 2026-08-21

Arnon's stated intent: *"all claude code keys should be actually in that new module — so the whole function would end up directly **referencing** the contract but not **expressing** it. Just that dependency alone is useful for static analysis and review purposes."*

**So the deliverable is an import edge**, not a tidier file. Consolidating turns *"does this module touch the external contract?"* into a checkable edge — the *"name the declaration"* principle from `.claude/rules/evidence-before-fixing.md`, which is what separates a strong conformance check from a heuristic.

## THIS IS NOT GREENFIELD — two modules are already partly it

### `toolguard/tool_spec.py` — roughly 60% contract already

- `ToolKind` (`COMMAND`/`FILE`) — a fact about Claude Code's tools
- `ToolSpec.payload_key` — **a Claude Code wire field** (`"command"`, `"file_path"`)
- `payload_key(tool_name)` — a function whose *sole* purpose is dealing with the external contract, which is exactly Arnon's move-it criterion

**But its docstring frames it as toolguard's own registry** — *"the tools toolguard knows how to govern"* — so the contract nature is invisible. The `additional_supported_tools` extension point genuinely is toolguard's, so this module is **mixed**, not misplaced.

### `toolguard/constants.py` — explicitly mixed

| contract | toolguard's own |
|---|---|
| `BUILTIN_TOOLS` (re-export) | `STATUS_EXECUTED` / `REFUSED` / `ASK` / `ERROR` / `UNKNOWN` |
| `FILE_TOOLS` (re-export) | `GIT_TIMEOUT_SECONDS` |
| `DEFAULT_COMMAND_PAYLOAD_KEY = "command"` | `DIST_NAME` |

Its own docstring calls it *"a single home for small vocabularies otherwise re-declared at multiple call sites"* — true, and it makes no distinction between the two kinds. **That mixing is the defect 85 names, already present in the module built to reduce duplication.**

## The scattered wire literals — concentrated, which is good news

| key | modules |
|---|---|
| `tool_name`, `tool_input`, `hookSpecificOutput`, `permissionDecision`, `permissionDecisionReason` | **`hook.py` only** |
| `hook_event_name`, `session_id` | `hook.py`, `testing/sandbox.py` |
| `cwd` | `hook.py`, `session_start.py`, `testing/sandbox.py` |
| `additionalContext` | `hook.py`, `rule_entry.py`, `rule_sort.py`, `testing/sandbox.py` — **the most spread** |

**The wire protocol is almost entirely `hook.py`'s**, which makes chunk 1 far smaller than the ticket's framing suggests. `additionalContext` is the outlier and the one that will actually exercise the new import edge.

## New since the ticket was written

**`STRIPPED_WRAPPERS`** — added to `toolguard/parser/command_extractor.py` by ticket 82 (`221eba9`), carrying the fetched doc quote and date. **This is contract material sitting in the parser**, and it is the clearest single example of what 85 is for. It also proves the problem is *ongoing*: the campaign added contract material to a non-contract module three commits ago, correctly, because there was nowhere else to put it.

## Revised chunk decomposition

The punch list's 4 chunks assumed greenfield. Given the map:

| chunk | scope | est |
|---|---|---|
| **85a** | Create the module. Move the **wire protocol** — the `hook.py` literals plus `additionalContext`'s four sites. Mostly one module in, one import edge out | 1.5h |
| **85b** | Move `payload_key`, `ToolKind`, and the contract half of `constants.py`; leave `additional_supported_tools` and the `STATUS_*` vocabulary where they are. **The judgement chunk** — `tool_spec.py` is genuinely mixed | 2h |

**~6.5h, down from 8h**, because two of the three homes already half-exist.

## The trap to state in every chunk's brief

**Arnon's criterion is precise and easy to over-apply**: *"Functions that mix references to external contract **structures** but have toolguard-specific logic **should not** be moved."*

`payload_key(tool_name)` moves — its whole job is the contract. `hook.py`'s request handling does **not** move — it references the contract and adds toolguard's logic. **An implementer optimising for "no contract literals outside the module" will move too much.** The test is whether the function's *purpose* is the contract, not whether it *mentions* it.
