## §1 was never an AUTOMATIC escalation, and both the ticket and my brief got this wrong

The `uv run alembic` `ask -> allow` escalation is produced by **`propose_broadening_consolidations`** (families 3-4), not by `propose_consolidations` (families 1-2). The module's own docstring:

> *"The module's other half, `propose_broadening_consolidations`, is not part of that scheme: it enumerates rewrites that DELIBERATELY admit more, gates nothing, and attaches evidence for a human to judge."*

and on the proposal class:

> *"A broadening DELIBERATELY admits more commands than the union of the rules it replaces, so it is never auto-applied."*

It **already received the corpus** before ticket 20 (`maintenance.py:210`). So:

- **The ticket's own "Fix direction" §2 is wrong** where it says wiring the corpus *"would have caught §1 and §2 on any real corpus"*. It cannot reach §1 at all.
- **My 20a brief inherited that error** and asked the implementer to demonstrate the escalation is now rejected. **The implementer measured it, refused the demonstration as impossible in scope, and substituted the ticket's §3 example** — a genuine family-2 shape the fix does catch.

§1's real content is therefore: *a human-judged proposal carried a warning field whose docstring said the danger was unreachable.* **The docstring is fixed, so §1 is done.** It was never the automatic privilege escalation its heading claims.

# THE BROADENING DISPUTE, resolved 2026-08-21 — three parties, all partly wrong

20a's repair deleted a docstring claim that *"a pure removal can never broaden a decision, so the tightening check is where a corpus actually does work here."*

**Four positions existed:**

| party | claim |
|---|---|
| ticket 20's own amendment | broadening by removal *"looks unreachable"* — a direct probe gave `broadened: 0` |
| the reviewer | **measurably false** — 54 of 6,300 replayed removals broadened, with a worked `ask -> allow` example |
| the implementer | **could not reproduce** the worked example; the ask pattern's specificity beats both rules, so the command stays `ask` |
| me, initially | sided with the reviewer and told the implementer the claim was *"measurably false"* |

**Measured: the implementer is right about the worked example, and the reviewer is right about the claim.**

The reviewer's specific config does **not** broaden — reproduced independently, `ask -> ask`. A search over allow/ask/command combinations found **0** `ask -> allow` broadenings. The `ask -> allow` route the example describes does not exist, because removing an allow cannot make a command more permitted.

**But the claim is still false, via a route none of the four positions named:**

```
allow=['echo:*'], no_match_fallback="deny"  ->  deny   "Command does not match any allow patterns"
allow=[],         no_match_fallback="deny"  ->  ask    "No Bash permission rules configured"
```

**An emptied allow list leaves the fallback path entirely** and takes a "no rules configured" branch that yields `ask`. And `replay.py:10` classifies *"deny -> ask"* as **broadened**.

So a pure removal broadens whenever it empties the allow list under a deny fallback. **Deleting the causal clause was correct**, and for a better reason than the one I gave.

## What this is an instance of

**A false universal, and every party reasoned about the wrong mechanism.** The reviewer inferred the right verdict from a wrong example; the implementer refuted the example and read that as refuting the verdict; the ticket predicted unreachability from the same partial mechanism; I took a side instead of asking *"is there a third route?"*

**The generalisable move: when two careful parties disagree about whether X can happen, neither one's mechanism is likely to be the whole story.** The productive question is not *"who is right"* but *"what path has nobody described?"* Here it was reachable in three commands once asked.

**Reachability caveat, stated rather than assumed**: family 2 removes a rule *because another subsumes it*, so at least one allow survives and it probably cannot empty the list. **The claim as written is false regardless** — and the check costs nothing, so the insurance stands whether or not this family reaches it.
