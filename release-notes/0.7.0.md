# toolguard 0.7.0 -- 2026-09-07

Claude Code's own permission mode now reaches the decision. Until this release toolguard recorded `permission_mode` in the log and nothing else; it never affected a verdict. Four new settings put it to work, and every one of them is a **handoff point** rather than a loosening: a declaration of how much you trust Claude Code's own auto-mode classifier for one specific class of case toolguard cannot decide on its own.

That framing is the point of the release, and it is now written down. See [Auto-mode with toolguard](../docs/auto-mode.md#division-of-labour-toolguard-vs-auto-mode-guidance).

## The division of labour, stated plainly

toolguard decides by exact pattern match; the classifier decides by semantic judgement. Each is strong exactly where the other is blind, and toolguard's blind spot is **constitutive, not an unimplemented gap** -- a compound command it cannot decompose, a heredoc, foreign inline code, a script whose contents it never sees. The ASK floor and `undecidable_fallback` exist to announce that blind spot, not to paper over it.

The corollary is a design smell worth naming: *"make toolguard smarter so it can handle X."* If X requires reading intent, the answer is the classifier, not a cleverer rule.

## `no_match_fallback_in_auto_mode` and `undecidable_fallback_in_auto_mode`

```toml
no_match_fallback_in_auto_mode = "allow_with_warning"
undecidable_fallback_in_auto_mode = "allow_with_warning"
```

Each resolves in place of its base setting **only while Claude Code's `permission_mode` is its `auto` mode**, so the same project stays strict the moment you return to an interactive session, with nothing to remember to tighten back up.

They are two settings rather than one flag on purpose. Trusting the classifier with a command toolguard read and simply had no rule for is a different judgement from handing it one toolguard could not read at all, and a single flag would force the same answer to both.

**Only the ASK tier relaxes.** `deny`, `hard_deny`, and the parse-failure floor resolve identically regardless of mode. There is no configuration that makes auto mode skip a `deny` rule or a `hard_deny` entry.

`toolguard-audit` reports both alongside the base settings, but only when the auto-mode value is configured *and* looser than the base one -- an unset auto setting is already covered by the base finding.

## `auto_mode_behavior` -- one rule declaring its own decision for auto mode

```toml
[permissions]
ask = [
    { match = "Bash(git push:*)", auto_mode_behavior = "allow" },
]
```

Rides the same structured-entry mechanism as `additionalContext`, so it composes with all four pattern dialects rather than adding a fifth. Any list, any direction: an `ask` widening to `allow` is the common case, but narrowing is equally valid, and a `deny` rule may widen to `allow` where the classifier is trusted as a second, independent gate.

`[hard_deny]` is the one exception and it is absolute -- a hard-deny entry's enrichment metadata is never exposed at all, so no permission-mode declaration on any entry can carve an exception out of it.

**A rule carrying `auto_mode_behavior` competes on its declared decision's precedence, not on the list it is written in.** Matching is deny-first within a level, so a `deny`-list rule declaring `allow` is matched *as* an allow and no longer wins deny-first precedence over a sibling deny that still applies. Provenance still names the rule's real list.

## `program_source` -- constrain a rule to material toolguard can see

```toml
[permissions]
allow = [
    { match = "Bash([regex]^uv run python\\b)", program_source = "file" },
]
```

The distinction is **visibility, and it is binary**: is the executable material in a file, or not. Material in a file is invisible twice over -- to the human at an ASK prompt, who cannot see inside it, and to toolguard, which cannot match against file contents. A redirect from a file counts as a file; the question is where the material is, not how it arrived.

A rule carrying `program_source` matches only when the classification agrees. Otherwise **the rule did not match at all** -- it is filtered out before matching runs, so pattern order does not matter and a sibling rule for the same command is unaffected.

Scope is command resolution only. On a Read/Write/Edit rule the key is rejected at config time with an error naming the key and the tool.

## The auto-mode trace

Every call that resolves through a fallback while `permission_mode` is auto appends one record to `logs/toolguard-automode-YYYY-MM-DD.jsonl`. It is a read-only side channel: nothing in the decision path reads it, and a write failure never changes a verdict.

Each record's `fallback_cause` is a **triage code**, because each value implies a different response -- `no_match` is addressable by writing a rule, `undecidable` never can be, `parse_failure` means fixing the config, and `unknown` means investigating rather than assuming. It records what toolguard deferred, never the classifier's own verdict on the same call.

## Unknown enrichment keys degrade instead of failing

An unrecognised key on a structured rule entry now warns rather than erroring, so a config written for a newer toolguard still loads on an older one.

## Documentation corrections, all of them fail-silent before this release

- **`auto-mode.md` defined "auto-mode" as `acceptEdits`/`bypassPermissions`/"or similar".** toolguard keys on `permission_mode == "auto"` by exact equality, so the page's own recommended setting would silently never fire for the readers it addressed. It now names the `auto` mode specifically and says what to configure under the others.
- **`security.md`'s guarantee that an ASK is never a silent allow is now measured rather than asserted.** A new manual test drives a real Claude Code session per permission mode; a rule resolving to ASK stopped the command under `default`, `acceptEdits`, `dontAsk` and `bypassPermissions` alike, with a control confirming the same command ran under `bypassPermissions` when the rule allowed it. See [`test/manual/`](../test/manual/README.md), and re-run it after a Claude Code upgrade.
- The `undecidable_fallback` reference now says that the foreign-inline-code floor recognises a **fixed, non-exhaustive** interpreter list. An interpreter outside it resolves through `no_match_fallback` like any other unmatched command.

## Upgrading

No configuration change is required: every new setting is optional and unset behaves exactly as 0.6.1 did. Adopt the two `_in_auto_mode` fallbacks first if you run unattended sessions -- they are the ones that replace loosening a base setting for every mode.
