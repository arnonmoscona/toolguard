# toolguard 0.7.1 -- 2026-09-10

A structural release. Nothing about how a decision is reached changed, and no configuration key, CLI flag or pattern semantic moved. What changed is where the code lives, what the layering rules are allowed to say, and one thing the hook is no longer allowed to do.

## Every module now lives in a layer package

41 loose top-level modules moved into packages named for the architecture layer they belong to: `integration`, `foundation`, `decision_model`, `install`, `observability`, `configuration`, `engine`, `runtime`, `tooling`, `support`. Four modules stay flat because they are entry points rather than layer members -- `hook.py`, `session_start.py`, `subagent.py` and `api.py`. The existing `parser/`, `tools/`, `scripts/` and `testing/` packages were left alone.

If you import from toolguard directly (there is no reason to; `toolguard.api` is the public surface), the import paths have changed.

## The layer graph is now declared as data, and the gate is acyclicity

`.pyscn.toml` gained an `[architecture.dag]` table naming, for each layer, the layers it may reach. It is a **minimal** edge set: 11 edges, from which `tools/architecture_fitness.py --layers` computes the transitive closure and checks that `[[architecture.rules]]` equals it.

This changes what the check is worth. The old flat allow-list was both the specification and the thing satisfied -- a violation could be resolved by editing the list. Acyclicity cannot: a cycle is a fact about the declared graph that no amount of editing the code will make legal, and it is reported before anything else. `--layers` also prints the closure, so adding one transitive edge shows you everything it just granted.

## `decision_model`: `engine` and `parser` can no longer reach `configuration`

The old `config_types.py` held two unrelated things: the vocabulary a decision is expressed in, and the types describing a configuration file. The engine needed the first and was therefore importing the second, which put a dependency on the whole `configuration` package underneath the lowest layers of the decision path.

18 names moved to a new `decision_model` package (`rule_entry.py` and `vocabulary.py`); 4 stayed behind in `configuration/config_types.py`. `decision_model` sits below both `engine` and `configuration`, and the DAG now forbids the edge that used to exist.

## Automatic migration moved off the hook path

**This is the one user-visible change.** With `auto_migrate = true`, a permission migration used to be triggered by the PreToolUse hook -- on the live decision path, at most once per calendar day per project. It now runs from `session_start` instead, with the same once-per-day throttle.

Two reasons. The migration workflow reports progress to stdout, and for the hook stdout is the channel carrying its JSON decision. And a backup-and-rewrite of configuration files does not belong inside a call working to a tens-of-milliseconds budget.

What this means in practice: migration happens slightly later -- at the start of a session rather than on the first governed command within it. Until it runs, the patterns in `settings.local.json` still take effect, because Claude Code is still reading them; nothing is unprotected in the interval.

## A new fitness check: `--privates`

`tools/architecture_fitness.py --privates` fails on a cross-module import of an underscore-prefixed name. Nine such imports existed and were fixed -- either the import should not have existed, or the name should not have been private. It is now a pre-push gate alongside `--stdlib`, `--ambient` and `--layers`.

## Bug fix

`install_provenance` resolved the installed package root from the wrong base, so provenance reporting could name a path that was not where toolguard was actually installed. It now resolves from `toolguard.__file__`.

## Documentation

`docs/architecture-as-built.md` gained a table of contents, a description of what each package is for, and rendered module-dependency diagrams for the hook path and for `toolguard/tools/`. Two claims in it were false and are corrected: the hook no longer triggers a migration, and the guarded-write section said otherwise one section later.

`docs/native-pattern-reference.md` is now listed in `llms.txt` and README -- it is the file every other doc defers to on native semantics, and it was reachable only from inside other docs. Its wildcard quotes were re-verified against Claude Code's published documentation on 2026-09-10 and **replaced**: the page had been rewritten since 2026-08-20, and the new text adds a constraint the old quotes did not carry. One new `[native]` divergence was measured and recorded in the same pass, and filed as **TOO-81**: `[native]` does not implement the `:*` trailing-wildcard shorthand, so a rule like `[native]git:*` matches nothing. The unmarked syntax is unaffected. That ticket carries a wider question, because measuring the defect found two more with the same cause and no `[native]` rule in use anywhere: whether the pattern type should be folded into the unmarked syntax rather than patched.
