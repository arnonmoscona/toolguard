# toolguard 0.6.1 -- 2026-08-28

A packaging fix with one new command. It closes the gap that let 0.6.0's skill fixes ship without reaching anyone who already had the skills installed.

## The skills now ship inside the package

Until now `skills/` sat beside the package and was excluded from the wheel, so an installed toolguard had no copy of its own skills. `toolguard-install install-skills` therefore had to be pointed at a repository -- a checkout or a git URL -- and `uv tool upgrade toolguard` upgraded the binary while leaving the installed skills exactly as they were.

That is not a theoretical gap. 0.6.0 fixed two security-audit rules that **matched no command ever**, and anyone who upgraded to 0.6.0 kept the broken skill, because nothing copied the fix out of the new package.

The skills and the manifest are now force-included into the wheel at `toolguard/_bundled/`, so the installed distribution carries the skills belonging to the build that is running.

## `toolguard-update-skills`

```bash
uv tool upgrade toolguard
toolguard-update-skills
```

Force-refreshes the user-scope skills in `~/.claude/skills/` from the copy inside the installation. No network, no git, no `--source` argument to get right, and no way for the skills to be a different version from the binary that governs your session.

- **Always overwrites**, because an unchanged copy is the failure being fixed. `install-skills` is a deliberate no-op on an existing directory, which is correct for an installer and wrong for a refresh.
- Each replaced skill is copied whole into `~/.toolguard/backups/<skill>-<timestamp>/` and recorded in the install journal with its reverse, before anything is written.
- `--list` prints what would be written, and where it would be read from, without writing anything.

`toolguard-install install-skills` keeps its job: the first install, before toolguard exists on the machine, and project-scope installs. `toolguard-update-skills` is the steady-state refresh.

## The bundled skill list has one declaration

`[tool.toolguard] bundled_skills` in `pyproject.toml` now names the shipped skills, and `install-skills`, `skills-status` and `update-skills` all read it instead of each holding their own copy. Adding a skill is a one-line edit in one file.

Two tests pin the declaration against reality in both directions: every declared skill must exist under `skills/`, and every directory under `skills/` must be declared -- an undeclared skill is one all three commands silently skip.

`install-skills --source` reads the manifest belonging to the **source**, so installing from an older tag installs the skills that tag declared, not the ones this build declares. A `--source` directory holding nothing but `skills/` remains valid input and falls back to this installation's list.
